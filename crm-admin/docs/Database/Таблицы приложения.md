# Таблицы приложения

Собственные таблицы crm-admin (в отличие от копий корпоративных — см. [[Справочники шаблонов]] и [[Слой B (процессные таблицы)]]). Живут в схеме `app` (аутентификация, ACL, цепочки, настройки панели) и `arch` (журналы). Создаются миграциями `V2__auth.sql`, `V3__journeys.sql`, `V4__admin_log.sql`, `V7__panel_settings.sql` (+ V6 добавляет две колонки в `app.journeys`). В прод-профиле Flyway выключен — эти таблицы там создаются вручную теми же скриптами.

## app.users — учётные записи

Источник: `src/main/resources/db/migration/V2__auth.sql`, entity `src/main/java/ru/banki/crm/domain/AppUser.java`. Пользователи входят по корпоративному email с самостоятельно выбранным паролем (BCrypt). Роль — уровень возможностей, видимость разделов — отдельно в `user_sections`. Подробно о модели доступа — [[Безопасность и RBAC]] и [[Пользователи и доступ]].

| Колонка | Тип | Смысл |
| ------- | --- | ----- |
| `id` | `bigserial PK` | Суррогатный ключ |
| `email` | `text NOT NULL UNIQUE` | Логин; домен может ограничиваться настройкой `app.email-domain` (env `APP_EMAIL_DOMAIN`, пусто = без ограничения) |
| `password_hash` | `text NOT NULL` | BCrypt-хэш пароля |
| `display_name` | `text` | Отображаемое имя |
| `role` | `text NOT NULL DEFAULT 'READER'` | `CHECK (role IN ('READER','EDITOR','ADMIN'))` — читатель / редактор / администратор |
| `enabled` | `boolean NOT NULL DEFAULT true` | Выключенный пользователь не может войти |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | Момент регистрации |

Первый супер-админ создаётся идемпотентно при старте приложения: `ru/banki/crm/config/AdminBootstrap` (CommandLineRunner) читает `app.admin.email`/`app.admin.password` (env `ADMIN_EMAIL`/`ADMIN_PASSWORD`), и если такого email ещё нет — создаёт пользователя с ролью `ADMIN` и **всеми** разделами. Если env не заданы — просто пишет warning и пропускает шаг.

## app.user_sections — видимость разделов (ACL)

| Колонка | Тип | Смысл |
| ------- | --- | ----- |
| `user_id` | `bigint NOT NULL REFERENCES app.users(id) ON DELETE CASCADE` | Пользователь; строки удаляются вместе с ним |
| `section_id` | `text NOT NULL` | Идентификатор раздела UI |

PK составной: `(user_id, section_id)`. Канонический список id — `ru/banki/crm/service/Sections.java`: `home`, `deviations`, `onelink`, `admin` (Мастер коммуникаций), `templates` (Список шаблонов), `dashboard`, `journeys` (Цепочки / Flow Builder), `access` (Управление доступом). Комментарий в V2 перечисляет старый набор без `journeys` — актуален именно код (`Sections.ALL`, `Sections.isValid()` валидирует входящие id).

## app.journeys — цепочки (Flow Builder)

Источник: `V3__journeys.sql` + две колонки из `V6__flow_layer_a.sql`; entity `src/main/java/ru/banki/crm/domain/Journey.java`. Вся схема цепочки (узлы, связи, позиции на канве) хранится **одним jsonb-документом** и читается/пишется атомарно — никаких таблиц «узлов» и «рёбер».

| Колонка | Тип | Смысл |
| ------- | --- | ----- |
| `id` | `varchar(36) PK` | UUID-строка, генерируется приложением |
| `name` | `text NOT NULL` | Название цепочки |
| `kind` | `varchar(10) NOT NULL DEFAULT 'online'` | `CHECK (kind IN ('online','offline'))`. Онлайн-цепочка стартует с Income event, оффлайн — с Time event (валидация в `MaterializationService.validate`) |
| `continues_journey_id` | `varchar(36) REFERENCES app.journeys(id) ON DELETE SET NULL` | Для offline: информационная метка «продолжение какой online-цепочки». На логику не влияет |
| `definition` | `jsonb NOT NULL` | `{nodes:[...], edges:[...]}` в формате `ru/banki/crm/dto/JourneyDtos` |
| `updated_by` | `text` | Email последнего редактора |
| `updated_at` | `timestamptz NOT NULL DEFAULT now()` | Момент последнего сохранения |

Формат `definition` (см. `JourneyDtos.JourneyNode` / `JourneyEdge`):

- узел: `id` (клиентский, стабильный внутри цепочки), `type` (`comm | subflow | assignment | decision | pause | loop | createRecords | updateRecords | getRecords | deleteRecords | startIncome | startTime`; `null` в старых данных = `comm`), `day` (день отправки comm-узла; в UI поле readonly и автоподставляется из `sending_day` шаблона), `channel` (`sms|push|email|cc`), `templateCode`, `title`, `note`, `active`, `posX`/`posY` (координаты Drawflow), `props` — map строк с полями, специфичными для типа (у Time event, например, `crontab`, `process_name`, `sql_steps` — JSON-массив SQL-шагов);
- ребро: `from`, `to`, `fromPort` (`output_1`/`output_2` у Decision/Loop).

Работа с таблицей — `ru/banki/crm/service/DbJourneyService` (включается при `app.journeys.mock=false`; в docker-compose это только контур **test**, prod/preprod пока живут на in-memory `MockJourneyService`, `JOURNEYS_MOCK=true`). Вложенная цепочка (Subflow) — это обычная строка `app.journeys` **без стартового узла** (autolaunched-модель): её можно сохранить, но отдельно материализовать нельзя; при материализации родителя она разворачивается рекурсивно. Ссылку на цепочку хранит и слой A: `flow.d_event.journey_id` (`ON DELETE SET NULL`). См. [[Цепочки (Journeys)]], [[Flow Builder (цепочки)]], [[Материализация (Flow)]].

Демо-строка `demo-welcome` заезжает сидом `V901__seed_journeys.sql` (только профиль `docker`).

## app.panel_settings — настройки панели (key → jsonb)

Источник: `V7__panel_settings.sql`; работает с таблицей `web/PanelSettingsController.java` (native SQL через `EntityManager`, JPA-сущности нет). Хранилище произвольных серверных настроек панели для настроечной админки `/settings`.

| Колонка | Тип | Смысл |
| ------- | --- | ----- |
| `key` | `varchar(64) PK` | Имя настройки; валидируется контроллером регуляркой `[a-zA-Z][a-zA-Z0-9_-]{0,63}` |
| `value` | `jsonb NOT NULL DEFAULT '{}'` | Произвольное значение |
| `timestamp_upd` | `timestamptz NOT NULL DEFAULT now()` | Момент последнего изменения (обновляется upsert-ом) |

Первый (и пока единственный) ключ — **`appSections`**: конфиг «приложение App Launcher → доступные разделы панели» вида `{ "Маркетинг": ["home","comms","dash"], ... }`; **пустой объект = все разделы всем приложениям** — именно его вставляет сид в V7 (`ON CONFLICT DO NOTHING`). Права: `GET /api/panel-settings/{key}` — любой аутентифицированный (оболочка SPA применяет конфиг при загрузке через `syncAppSections()` в `api.js`, зеркало — `localStorage crmpanel:appSections`), `PUT` — только ADMIN; каждая запись журналируется в `arch.t_admin_log` (слепок строки после изменения). См. [[Оболочка панели (shell)]], [[Управление доступом и вход]] и [[REST API]].

## arch.arch_log — триггерный аудит шаблонов

Источник: `V1__template_schema.sql`. Заполняется **самой БД** — триггерами `trg_audit_push/email/sms/cc` (AFTER INSERT OR UPDATE OR DELETE, FOR EACH ROW) на четырёх канальных таблицах шаблонов, через функцию `arch.log_change()`.

| Колонка | Тип | Смысл |
| ------- | --- | ----- |
| `id` | `bigserial PK` | — |
| `table_name` | `text NOT NULL` | `TG_TABLE_SCHEMA || '.' || TG_TABLE_NAME`, напр. `notice.push_template` |
| `operation` | `text NOT NULL` | `INSERT` / `UPDATE` / `DELETE` (значение `TG_OP`) |
| `row_pk` | `text` | Бизнес-ключ строки: `COALESCE(code, id, segment)` из jsonb-образа NEW, затем OLD |
| `changed_by` | `text` | `current_setting('app.current_user', true)` — email, выставленный приложением |
| `changed_at` | `timestamptz NOT NULL DEFAULT now()` | Момент операции |

Автора триггер узнаёт из транзакционного GUC `app.current_user`: перед мутацией `TemplateService` вызывает `ru/banki/crm/service/AuditContext.mark()` → `set_config('app.current_user', <email>, true)` (третий аргумент `true` = значение живёт до конца транзакции). Механизм включается флагом `app.audit.enabled` (по умолчанию `true`). Если мутация пришла мимо приложения (руками в БД) — строка аудита всё равно появится, но `changed_by` будет NULL.

## arch.t_admin_log — журнал действий админки

Источник: `V4__admin_log.sql`. В отличие от `arch_log` заполняется **приложением** (`ru/banki/crm/service/AdminLogService`), структура 1:1 по прод-спецификации `t_admin_log`. Физическое имя конфигурируется: `app.tables.admin-log` ← env `ADMIN_LOG_TABLE`, по умолчанию `arch.t_admin_log`.

| Колонка | Тип | Смысл |
| ------- | --- | ----- |
| `id` | `bigint GENERATED BY DEFAULT AS IDENTITY PK` | — |
| `table_name` | `varchar` | Физическое имя затронутой таблицы (канальной или таблицы слоя B) |
| `operation` | `varchar` | `INSERT` / `UPDATE` / `DELETE` |
| `old_row` | `jsonb` | Образ строки; **семантика зависит от операции** (см. ниже) |
| `action_user` | `varchar` | Email текущего пользователя (`CurrentUser.email()`) |
| `timestamp_cr` | `timestamp NOT NULL DEFAULT now()` | Момент записи |

**Семантика `old_row`** (задокументирована в `AdminLogService`): для `UPDATE` и `DELETE` — строка **до** изменения/удаления; для `INSERT` — **созданная** строка (иначе о факте заведения не оставалось бы никаких данных). Образ строки берётся native-запросом `SELECT to_jsonb(t)` по суррогатному `id` (метод `rowJson`, с предварительным `em.flush()`), т.е. в jsonb — точные имена колонок БД.

Кто пишет:
- `TemplateService.create/update/delete` — каждая операция над шаблоном, в той же транзакции;
- `MaterializationService.materialize` — **каждая** вставка в слой B логируется через `AdminLogService.logTable(table, "INSERT", rowJson)` параллельно с записью в `flow.t_materialization`;
- `PanelSettingsController.put` — каждая запись настройки панели (`app.panel_settings`, операция `UPDATE`, слепок строки после изменения).

См. также [[Аудит и журналирование]] и [[Схема БД]].
