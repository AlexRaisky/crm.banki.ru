# Схема БД

Обзор структуры базы данных CRM-админки. В dev-режиме поднимается собственная PostgreSQL 16 в Docker, а Flyway-миграции воспроизводят боевую (прод-идентичную) схему таблиц шаблонов 1:1 (те же имена схем/таблиц/типы). Позже возможно переключение на прод-БД сменой env — код при этом не меняется. См. также [[Развёртывание (Docker)]] и [[Overview]].

## Пять схем

| Схема | Назначение | Таблицы |
|---|---|---|
| `notice` | Уведомления/рассылки (push, email, SMS) | [[push_template (таблица)]], [[email_template (таблица)]], [[d_com_sms_template (таблица)]] |
| `callcenter` | Коммуникации колл-центра (обзвон, сегменты) | [[d_segment_properties (таблица)]] |
| `retention` | Ретеншн-сценарии | Схема создаётся (`CREATE SCHEMA IF NOT EXISTS retention`), но в текущих миграциях таблиц не содержит — зарезервирована под прод-схему |
| `arch` | Аудит изменений | [[arch.arch_log (таблица)]] |
| `app` | Аутентификация и RBAC приложения | [[app.users (таблица)]], [[app.user_sections (таблица)]] |

Схемы шаблонов (`notice`, `callcenter`, `retention`, `arch`) воспроизводят корпоративную БД. Схема `app` — собственная для нашего приложения (пользователи, роли, ACL разделов), в проде она добавляется к существующим корпоративным схемам.

## Таблицы шаблонов (4 «канала»)

Четыре канальные таблицы имеют общее ядро полей (`communication_name`, `communication_type`, `source`/`source_type`, `product_type text[]`, `trigger_type`, `sending_day`, `partner_name`, `aff_sub3`, `touch_point`, `business_communication_type`, флаги `marketplace`/`mobile_app`/`loyalty`/`dialog`/`news`/`national_rating`/`active_flag`) плюс спец-поля канала. Физические имена таблиц вынесены в `application.yml` (`app.tables.push/email/sms/cc`), чтобы переключение окружений не требовало правок кода.

- **push** → `notice.push_template` (PK `id` bigint, seq `push_template_id_seq`)
- **email** → `notice.email_template` (PK `id` bigint, seq `email_template_id_seq`; бизнес-код здесь `trigger_code`)
- **sms** → `notice.d_com_sms_template` (PK `id` integer, seq `d_com_sms_template_id_seq`)
- **cc** → `callcenter.d_segment_properties` (PK `id` bigint, seq `d_segment_properties_id_seq`; бизнес-номер `segment`)

## Механизм аудита

Каждая из 4 таблиц шаблонов имеет триггер `AFTER INSERT OR UPDATE OR DELETE FOR EACH ROW` (`trg_audit_push`, `trg_audit_email`, `trg_audit_sms`, `trg_audit_cc`), вызывающий функцию `arch.log_change()`. Функция пишет строку в [[arch.arch_log (таблица)]]: имя таблицы, операцию, бизнес-ключ строки (`COALESCE(code, id, segment)`) и автора.

Автор (`changed_by`) читается из настройки сессии `app.current_user` через `current_setting('app.current_user', true)`. Приложение выставляет её (email текущего пользователя) перед мутирующими запросами в той же транзакции — за это отвечает [[AuditContext]] (порт `set_config` из v2). Флаг `app.audit.enabled` в `application.yml` включает этот механизм.

## Стратегия dev → prod

- **Dev (профиль `docker`):** своя PostgreSQL в `docker-compose`; Flyway применяет `db/migration` (схема) + `db/seed` (демо-данные `V900__seed_dev.sql`). Все NOT NULL-колонки имеют DEFAULT, чтобы демо-данные и урезанная форма v1 вставлялись без ошибок.
- **Prod (профиль `prod`):** подключение к существующей корпоративной PostgreSQL; таблицы уже есть, поэтому Flyway отключён (`spring.flyway.enabled=false`). Datasource и физические имена таблиц задаются через env — правок кода не требуется.
