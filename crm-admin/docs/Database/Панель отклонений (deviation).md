# Панель отклонений (deviation)

Схема заведена миграцией `V65__deviation_schema.sql` под раздел [Панель отклонений](../Frontend/Панель%20отклонений.md). До неё раздел жил целиком в браузере: цифры приезжали из Excel, комментарии лежали в `localStorage`. Значит история была только у того, кто последним нажал «Сохранить в Excel», и доказать «это отклонение мы видели и разобрали» было нечем.

Три слоя разделены намеренно: факт живёт независимо от расчётов, расчёты — снимками, разбор — отдельно от того и другого.

## Таблицы

| Таблица | Что хранит |
| --- | --- |
| `d_revenue_daily` | Факт: выручка за день в разрезе `group1` (направление), `group2` (продукт) и `channel`. Та самая плоская таблица «Данные_день_продукт» из файла |
| `t_load` | Откуда пришли цифры: загрузка файла из раздела (`kind = file`) или регулярная подтяжка из источника (`etl`), период, сколько строк новых и обновлённых |
| `d_threshold` | Пороги: окно медианы, всплеск 20% и 60%, снижение 14 дней / 20% / 30%. Одна строка — это настройка инструмента, а не справочник |
| `t_run` | Снимок расчёта: период, счётчики и **пороги, с которыми считали** |
| `t_run_daily` | Ряд «факт против нормы»: выручка, база-медиана, отклонение, день-к-дню |
| `t_run_flag` | Дни-отклонения: направление, сила, метка, авто-гипотеза, топ-драйверы (`jsonb`) |
| `t_run_decline` | Плавные снижения: уровень, период, глубина |
| `t_run_monthly` | Помесячная сводка: сумма, среднее в день, мин, макс, волатильность, MoM |
| `t_run_checkday` | «Требуют точечной проверки»: день и что именно замечено |
| `t_note` | Разбор: комментарий и статус гипотезы, автор и время правки |

## Почему так

**Уникальность `(fact_date, group1, group2, channel)`.** Дозагрузка того же дня обязана обновлять строку, а не добавлять вторую: без ограничения повторный импорт одного файла удвоил бы выручку и нарисовал бы всплеск на ровном месте.

**Режим `replace` чистит период.** Продукт, исчезнувший из нового файла, иначе остался бы в базе со старой цифрой и продолжал бы влиять на итог дня.

**Пороги дублируются в снимок.** Они меняются, а объяснять, почему день попал в отклонения, приходится спустя месяцы — по значениям, действовавшим на момент расчёта, а не сегодняшним.

**Снимки не переписываются.** Пересчёт после дозагрузки создаёт новый `t_run`; старые остаются как есть — в этом и смысл историчности.

**Разбор живёт вне снимков.** Иначе пересчёт обнулял бы работу, ради которой раздел и нужен. `object_key` — бизнес-ключ: для дня это дата, для тренда «уровень|дата начала». Тренд после дозагрузки может сдвинуть границу, и ключ перестанет совпадать; поэтому рядом лежит `snapshot` — уровень, период и глубина на момент написания, по которым запись можно узнать и перепривязать.

## API

`/api/deviations`, права по секции `deviations`: чтение — по секции, загрузка выручки — `ADD`, комментарии и пороги — `EDIT`.

| Метод | Путь | Зачем |
| --- | --- | --- |
| GET | `/revenue?from=&to=` | факт для расчёта в разделе |
| POST | `/revenue` | приём разобранного файла (`mode`: replace / append) |
| GET | `/loads` | журнал поступлений |
| GET/PUT | `/thresholds` | пороги |
| POST | `/runs` | сохранить снимок расчёта |
| GET | `/runs`, `/runs/{id}` | список снимков и один снимок целиком |
| GET/PUT | `/notes` | комментарии и статусы гипотез |

Расчёт (медиана, флаги, тренды) остаётся на клиенте: он уже написан, работает и в демо-режиме без сервера. Сервер хранит вход и результат — переносить арифметику на бэкенд значило бы держать две её копии и следить, чтобы они не разошлись.

## Что дальше

Сырьё пока приходит только загрузкой файла из раздела. Когда подключат источник, регулярная подтяжка пишет в те же таблицы с `t_load.kind = 'etl'` — заводить вторую историю поступлений не потребуется.
