# Как дорабатывать панель

Заметка для тех, кто заказывает и выкатывает доработки CRM-панели: куда писать заявку, что в ней должно быть, как правка доезжает до боевого контура и что делать, когда сломалось. Про устройство системы — [[Флоу системы]], про контуры и переменные — [[Среды и деплой]].

## Три контура и что можно на каждом

| Контур | Где открывается | Для чего |
| ------ | --------------- | -------- |
| **test** | `http://localhost:8082` через SSH-туннель | Здесь появляется всё новое. Данные не жалко: ломать можно. |
| **preprod** | `http://localhost:8081` через SSH-туннель | Репетиция боевого: смотрим на почти реальных данных. |
| **prod** | домен | Боевой. Сюда попадает только то, что проверили на тесте. |

Все три поднимаются **из одного образа** `crm-admin:local`, но контейнеры пересоздаются по отдельности. Отсюда правило: пересобрали образ — новый код получит только тот контур, который вы пересоздали. Прод продолжит работать на своей сборке, пока его не тронут.

Туннель с рабочей машины:

```
ssh -L 8081:127.0.0.1:8081 -L 8082:127.0.0.1:8082 user@server
```

## Как заказать доработку

Заявки живут в самой панели: **Настройки → Служебное → Бэклог** (раздел виден администраторам). Не в переписке и не в устном разговоре — оттуда они теряются.

Хорошая заявка отвечает на три вопроса, и все три нужны:

1. **Где** — раздел панели, страница, а лучше и конкретный шаблон или строка: «Планирование промо», «мастер, канал email», «отчёт ЧЕК СМС».
2. **Что мешает сейчас** — что именно происходит и чего вы ждали вместо этого. «Не работает» не годится: не работает по-разному.
3. **Каким должен стать результат** — как вы поймёте, что сделано.

Приоритет ставится в той же форме: **высокий** — мешает работать сегодня, **обычный** — надо сделать, **низкий** — хорошо бы. Исполнитель выбирается из списка супер-админов; можно оставить пустым.

Что дозрело до работы — переезжает в Jira задачей; бэклог для этого не замена, а место, где мысль не теряется, пока её обсуждают.

## Как правка доезжает до контуров

Порядок один и тот же, и сокращать его не стоит: тест → препрод → прод.

**1. Код.** Репозиторий `crm.banki.ru`, рабочая ветка `admin-panel`, приложение — в каталоге `crm-admin`.

**2. Забрать изменения на сервере:**

```
cd ~/crm.banki.ru && git pull
```

**3. Собрать образ.** Сборка описана у сервиса `app-prod`, но образ получается общий — это просто место, где живёт `build`:

```
cd ~/crm.banki.ru/crm-admin && docker compose -f docker-compose.yml -f docker-compose.server.yml build app-prod
```

**4. Пересоздать нужный контур.** Именно пересоздать (`--force-recreate`), а не перезапустить: `docker restart` не перечитывает `.env`, и новые переменные не подхватятся.

```
docker compose -f docker-compose.yml -f docker-compose.server.yml up -d --no-deps --force-recreate app-test
```

**5. Проверить.** Открыть раздел, ради которого всё делалось, и посмотреть логи старта:

```
docker logs --tail 40 crm-admin-app-test
```

**6. Раскатать дальше.** Те же команды с `app-preprod`, затем `app-prod`. После пересоздания прода перечитать nginx:

```
docker exec crm-admin-nginx nginx -s reload
```

### Что происходит с базой

Изменения структуры едут **миграциями Flyway** (`src/main/resources/db/migration`, файлы `V<номер>__описание.sql`) и накатываются автоматически при старте приложения — отдельной команды нет. Отсюда два следствия:

- миграция доезжает до контура **вместе с кодом**: пока контейнер не пересоздан, база не меняется;
- откат кода назад **не откатывает** миграцию. Если нужно вернуться, сначала обсудите, что делать со схемой.

Руками в прод-БД не ходим. Всё, что панель делает с боевыми таблицами, идёт через очередь синка — так это видно в журнале и повторяемо.

## Когда сломалось

Порядок осмотра — от общего к частному:

1. **Настройки → Служебное → Состояние системы.** Вердикт одной строкой и список проверок: что именно не так и что с этим делать. Там же видно, сколько данных в таблицах, докуда доехала очередь и какая версия собрана.
2. **Настройки → Интеграции → Карта интеграций.** Одна картинка: с кем панель разговаривает и что из этого сейчас не отвечает. Красная стрелка сразу показывает, где рвётся; клик по узлу открывает раздел, где это настраивается.
3. **Настройки → Переливы → Процессы переливов.** Проверить, не остановлен ли процесс человеком: остановленный перелив выглядит как «ничего не едет», но это чьё-то решение.
4. **Настройки → Переливы → Синхронизация шаблонов.** Очередь: сколько `PENDING`, есть ли `ERROR`. У записи с ошибкой видно текст отказа и кнопку повтора.
5. **Логи контейнера** — если предыдущее ничего не объяснило:

```
docker logs --tail 200 crm-admin-app-prod 2>&1 | grep -iE "error|exception|failed"
```

6. **Журнал действий** — кто что менял: `arch.t_admin_log` для данных, `app.schema_audit` для структуры базы.

Контур не открывается вовсе — сначала посмотреть, живы ли контейнеры:

```
docker ps -a --filter name=crm-admin --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
```

## Доступы

- **В панель** — учётка заводится в «Управлении доступом»; что человек видит, задаёт роль и матрица разделов ([[Безопасность и RBAC]]).
- **Супер-админ** — список почт в `ADMIN_EMAIL` (через запятую), закрепляется при старте. Их держат минимум двоих: свою учётку супер-админ отключить не может, это делает второй.
- **База через DBeaver** — по SSH-туннелю, порты 5432 (прод), 5433 (препрод), 5434 (тест). Роли в контурах разные: заведённая на проде роль на тесте сама не появится.
