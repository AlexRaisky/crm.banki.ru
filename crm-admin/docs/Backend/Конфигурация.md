# Конфигурация

Вся конфигурация — один `src/main/resources/application.yml` с тремя документами: базовый + профили `docker` и `prod`. Почти каждое значение параметризовано env-переменной с дефолтом (`${VAR:default}`), поэтому одна сборка запускается на всех средах без пересборки (см. [[Среды и деплой]]).

Значения читаются точечными `@Value` в компонентах — единого `@ConfigurationProperties` в проекте нет.

## Базовый профиль

### spring.datasource / jpa

| Ключ | Env | Дефолт |
|---|---|---|
| `spring.datasource.url` | `DB_URL` | `jdbc:postgresql://localhost:5432/crm` |
| `spring.datasource.username` | `DB_USER` | `crm` |
| `spring.datasource.password` | `DB_PASSWORD` | `crm` |

- `jpa.open-in-view: false` — сессия Hibernate не тянется в рендеринг (чистый REST).
- `hibernate.ddl-auto: none` — схему приложение **никогда** не создаёт через Hibernate; это делает Flyway (docker) или она уже существует (prod).
- `hibernate.jdbc.time_zone: Europe/Moscow` — timestamp'ы пишутся и читаются в московском времени, как в прод-БД.

### spring.flyway

`enabled: true`, `schemas: notice,callcenter,retention,arch,app`, `default-schema: app` (в `app` живёт таблица истории Flyway), `create-schemas: true`. Схемы `flow`, `tracker`, `scheduler`, `template`, `commapi`, `dictionary` в списке нет — их создают сами миграции через `CREATE SCHEMA IF NOT EXISTS`.

Схемы `notice` и `callcenter` в списке остались от первой версии: их локальные копии выпилены миграцией `V12`, и приложение с ними больше не работает. Актуальный состав миграций (**V1–V33**) — в [[Схема БД]].

### server

- `port: 8080` (внутри контейнера, наружу мапится compose-ом);
- `forward-headers-strategy: framework` — корректные схема и хост за реверс-прокси;
- `servlet.session.timeout: ${SESSION_TIMEOUT:7d}` — длинная сессия; после истечения вход восстанавливает remember-me кука;
- `servlet.session.cookie.name: ${SESSION_COOKIE:JSESSIONID}` — **своё имя куки на среду**: prod/preprod/test живут на одном хосте и с общим именем затирали бы друг друга;
- `error.include-message: always`, `include-binding-errors: always` — русские сообщения `ResponseStatusException` и bean-validation доезжают до SPA.

`springdoc.swagger-ui.path: /swagger-ui.html` — интерактивная документация API ([[REST API]]).

## Профиль docker

Активируется `SPRING_PROFILES_ACTIVE=docker` (compose ставит его всем средам). Смысл — **встроенная БД для local/dev/demo**: Flyway строит прод-идентичную схему и заливает демо-данные.

```yaml
spring.flyway:
  locations: classpath:db/migration
  out-of-order: true
```

Применяются только миграции схемы (`db/migration`, V1–V33). Сиды (`db/seed`: `V900__seed_dev.sql`, `V901__seed_journeys.sql`) **отключены** 30.07: `V900` наполняет канальные таблицы, удалённые в `V12`, и на чистом томе прогон падал (подробности — [[Схема БД]]). Записи о них в `flyway_schema_history` уже поднятых контуров вычищает `FlywaySeedCleanup` перед `migrate()`.

**Почему `out-of-order: true`**: сиды заняли версии V900+. На уже поднятой dev-БД Flyway успел применить V900/V901, и любая новая схемная миграция оказывается «младше» максимально применённой — по умолчанию Flyway такое отвергает. Флаг разрешает применять их задним числом и остаётся включённым как наследие того же порядка версий. Безопасно **только** для dev-БД этого профиля; на проде вопрос не стоит, там Flyway выключен.

## Профиль prod

Подключение к **существующей корпоративной** PostgreSQL: таблицы там уже есть, поэтому

```yaml
spring.flyway.enabled: false
app.audit.enabled: true
```

Обрати внимание: docker-compose в репозитории активирует профиль `docker` даже для контура «prod» — это локальная эмуляция трёх сред. Профиль `prod` предназначен для развёртывания против реальной корпоративной БД.

## Значения по средам (docker-compose.yml)

Три пары db+app (postgres:16 + `crm-admin:local`):

| | prod | preprod | test |
|---|---|---|---|
| контейнеры | `crm-admin-{db,app}-prod` | `-preprod` | `-test` |
| порт приложения | `${APP_PORT:-8080}` | `${APP_PORT_PREPROD:-8081}` | `${APP_PORT_TEST:-8082}` |
| порт БД наружу | `${DB_PORT:-5432}` | `5433` | `5434` |
| том БД | `crm_db_data` (прежнее имя — данные сохранены) | `crm_db_preprod` | `crm_db_test` |
| `APP_ENV` | `prod` | `preprod` | `test` |
| `FEATURES_DEV` | `false` | `false` | **`true`** |
| `JOURNEYS_MOCK` | `${JOURNEYS_MOCK:-false}` | `${JOURNEYS_MOCK:-false}` | **`"false"`** — цепочки в БД, нужно для материализации (FK `journey_id`) |
| `PROD_DB_URL` | `${PROD_DB_URL:-}` | `${PROD_DB_URL_PREPROD:-}` | `${PROD_DB_URL_TEST:-}` |
| `SESSION_COOKIE` | `CRMSID_PROD` | `CRMSID_PREPROD` | `CRMSID_TEST` |
| `REMEMBER_COOKIE` | `crm-remember-prod` | `crm-remember-preprod` | `crm-remember-test` |
| `REMEMBER_ME_KEY` | `${REMEMBER_ME_KEY:-…}-prod` | `…-preprod` | `…-test` |

Общие: `SPRING_PROFILES_ACTIVE=${SPRING_PROFILES_ACTIVE:-docker}`, `DB_URL=jdbc:postgresql://db-<среда>:5432/${DB_NAME:-crm}`, `DB_USER`/`DB_PASSWORD`, `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `APP_EMAIL_DOMAIN`, `REMEMBER_ME_DAYS=30`, `SESSION_TIMEOUT=7d`, `ETL_ENABLED`/`ETL_INTERVAL_MS`/`ETL_FULL_CRON`. Суффикс среды у ключа remember-me означает, что токены одной среды не валидны в другой даже при общем базовом ключе.

У db-сервисов healthcheck `pg_isready`; `app-preprod` и `app-test` ждут `app-prod` (`service_started`) — он собирает общий образ `crm-admin:local`. Порты по умолчанию биндятся на `${APP_BIND:-0.0.0.0}` / `${DB_BIND:-127.0.0.1}`; на сервере ставится `APP_BIND=127.0.0.1`, наружу приложения смотрят через nginx (`docker-compose.server.yml`). Детальная процедура деплоя — [[Среды и деплой]].

## EnvController

GET `/api/env` → record `EnvDto(name, devFeatures)` из `app.env.name` / `app.features.dev`. Доступен любому аутентифицированному; SPA красит по нему бейдж среды и решает, показывать ли dev-разделы NAV. Это **UI-переключатель**: API цепочек (`/api/journeys`, `/api/flow`) закрыт ролью ADMIN, а не флагом `FEATURES_DEV`.
