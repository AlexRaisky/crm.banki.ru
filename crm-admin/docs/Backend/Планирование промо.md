# Планирование промо

Раздел «Планирование промо» (section id `promo`) — общий календарь промо-коммуникаций команды. До него план жил в `localStorage` каждого браузера: у трёх планировщиков были три разные таблицы, и «общего» плана не существовало. Теперь строки лежат в `app.promo_plan`, правятся через `/api/promo/plan` и видны всем сразу.

Код: `service/PromoPlanService`, `web/PromoPlanController`, фронт — `static/js/promo.js`. Пути и коды ответов — [[REST API]].

## Таблица `app.promo_plan`

Заведена миграцией `V18__promo_plan.sql`, колонка `communication_name` добавлена `V24__promo_communication_name.sql`. Подробности схемы — [[Таблицы приложения]]; здесь только то, что важно для логики раздела.

## Конкурентная правка: `timestamp_upd` как версия строки

В разделе редактируется **отдельная ячейка**, а не форма целиком: `PATCH /api/promo/plan/{id}` c телом `{field, value, ver}`. `ver` — то значение `timestamp_upd`, которое видел клиент.

```sql
UPDATE app.promo_plan
   SET <поле> = :v, timestamp_upd = now(), updated_by = :u
 WHERE id = :id
   AND (CAST(:ver AS timestamptz) IS NULL OR timestamp_upd = CAST(:ver AS timestamptz))
```

- Обновлено 0 строк → сервис смотрит, существует ли строка: нет — `404 «Строку уже удалили»`, есть — **`409 «Строку изменил другой пользователь»`**. Раздел по 409 просто перечитывает план и не затирает чужое.
- Пустой/отсутствующий `ver` — правка без проверки версии (клиент версии не знает).
- Это **оптимистическая блокировка на уровне колонки-метки**, а не `@Version` JPA: правки идут нативным SQL, а отдельная колонка версии была бы дублем `timestamp_upd`.
- Ответ на успешную правку — строка целиком (с новым `ver`).

`DELETE` версию не проверяет: удаление — осознанное действие, конфликтовать там нечему.

Формат `ver` нормализован в сервисе (`instant()`): драйвер отдаёт `timestamptz` то как `Instant`, то как `Timestamp`/`OffsetDateTime`, и без приведения к ISO-8601 клиент получал бы разные форматы, а сравнение версий ломалось бы.

## Правило «одна запись = один канал»

Одна акция может идти в нескольких каналах, но в таблице каждой строке соответствует ровно один канал.

- **Заведение** (`POST`): в теле `chan` может быть массивом — сервис создаёт **столько строк, сколько каналов**, и возвращает их все. Канал можно не указывать вовсе — тогда создаётся одна строка с пустым каналом («требует заполнения»).
- **Смена канала** (`PATCH` поля `chan` списком): текущая строка забирает первый канал, остальные уезжают в **копии** этой же строки (`INSERT … SELECT` с новым каналом). Проверка версии применяется к исходной строке.
- Фронт группирует строки одной акции по ключу «дата + продукт + партнёр + уникальное имя/база», чтобы правила планирования считали мультиканальную акцию **одним промо**.

`id` для новой строки берётся заранее из последовательности (`SELECT nextval('app.promo_plan_id_seq')`): Hibernate считает нативный `INSERT` изменяющим запросом и результат `RETURNING` не отдаёт.

## Архивация статусов при чтении

`GET /api/promo/plan` перед выдачей вызывает `archiveSync()`: строки с прошедшей `plan_date` и статусом `запланировано` переводятся в `отправлено`. Раньше это делал каждый клиент при открытии раздела и тут же сохранял — на общей таблице это означало бы запись в БД с каждого открытия страницы. Теперь один `UPDATE` при чтении списка, и только если есть что менять.

Весь план отдаётся **целиком, без пагинации**: строк порядок сотен, а фильтры, вкладки «Актуальные/Архивные» и правила планирования считаются на клиенте по всему набору — постранично их не посчитать.

## Название коммуникации и колонка `communication_name`

В модели панели название коммуникации **собирается автоматически** по правилам Конструктора source: `{канал}_promo_{продукт}_{партнёр}_{уникальное имя}_{ддммгг}` (см. [[Обзор фронтенда]]). Если частей не хватает, грид показывает список недостающих полей.

Но при импорте календаря из Excel название приходит **готовым текстом** («Альфа-Карта», «ОСАГО от Ренессанс»), а партнёра и уникального имени в выгрузке нет — авто-сборка неполна. Для этого случая и добавлена миграцией `V24` колонка `communication_name`: грид показывает сохранённое название, когда авто-сборка не собирается.

## Импорт календаря (`scripts/promo_import.sql`)

Таблица наполнена импортом из `CRM-ПРОМО.xlsx` (лист «Календарь»): **115 строк = 77 промо**, где мультиканал («email, push») разложен по правилу «один канал = одна строка».

```bash
docker exec -i crm-admin-db-prod psql -U crm -d crm < crm-admin/scripts/promo_import.sql
```

- Требует применённой миграции `V24` — сначала раскатывается образ, потом запускается скрипт.
- Скрипт **безопасно перезапускать**: он сносит только свои прежние строки (`created_by = 'import:CRM-ПРОМО.xlsx'`), записи, заведённые людьми, не трогает. Всё в одной транзакции.
- Партнёр и уникальное имя в выгрузке отсутствуют — заполнены пустыми, название лежит в `communication_name`.

Демо-данными таблица не наполняется: пустой план — нормальное стартовое состояние.

## Что делает фронт

Серверная часть намеренно «тупая» — вся раскладка и проверки живут в разделе (`promo.js`):

- строки-разделители по датам, «+» добавляет запись на эту дату; форма новой записи открывается под шапкой таблицы;
- вкладки **«Актуальные» / «Архивные»** (по прошедшей дате отправки);
- **правила планирования** подсвечивают проблемные строки: не больше 1 тотала в неделю (2, если в уникальном имени есть `-cb` — ставка ЦБ); не больше 3 промо на один продукт в день и они должны идти в разных каналах; не больше 4 промо в день; в день с тоталом остальные промо в том же канале подсвечиваются;
- автообновление раз в 30 секунд, если раздел открыт и не идёт правка;
- выгрузка плана в CSV.

## Права

| Операция | Требуется |
|---|---|
| `GET` списка | READ на разделе `promo` |
| `POST` (завести) | ADD на `promo` |
| `PATCH` (правка поля) | EDIT на `promo` |
| `DELETE` | DELETE на `promo` |

`promo` входит в `Sections.WRITABLE` — то есть в матрице прав у роли осмысленны все четыре галки. ADMIN обходит матрицу целиком ([[Безопасность и RBAC]]).

Каждая операция пишется в журнал `arch.t_admin_log` (`AdminLogService.logTable("app.promo_plan", …)`): для `UPDATE`/`DELETE` снимок берётся **до** операции, для `INSERT` — после; при конфликте версий запись в журнал не попадает, чтобы не оставлять ложных следов. Падение журнала не роняет саму операцию. См. [[Аудит и журналирование]].
