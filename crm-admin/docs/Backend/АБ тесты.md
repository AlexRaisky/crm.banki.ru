# А/Б тесты

Журнал А/Б тестов — общая таблица команды: когда шёл тест, кто его инициировал, что проверяли, на каких шаблонах и к чему пришли. Раздел устроен по образцу [Планирование промо](Планирование%20промо.md) — та же схема «строки на сервере + правка по ячейке», поэтому здесь описано только своё, а общие механики не пересказываются.

Заведён миграцией `V26__ab_test.sql` (30.07.2026). Структура колонок — [[Таблицы приложения]], контракты ручек — [[REST API]].

## Колонки раздела

| Колонка в UI | Ключ в API | Колонка в БД | Смысл |
|---|---|---|---|
| Начало | `d1` | `date_start` | обязательна: по ней строится порядок (свежие сверху) |
| Окончание | `d2` | `date_end` | **необязательна**: у идущего теста даты может ещё не быть; в таблице — дата или «—» |
| Статус | `status` | `status` | **проставляется вручную**: `запланировано` / `идёт` / `завершён` (выпадающий список). `идёт` подсвечивает строку зелёной полосой; статус — источник для фильтра и сводки. См. ниже |
| Что тестировали | `subject` | `subject` | гипотеза |
| Шаблоны | `templates` | `templates` | какие шаблоны участвовали; свободный текст (моноширинный в таблице) |
| Кто инициировал | `owner` | `owner_name` | заказчик теста |
| Кто тестировал | `tester` | `tester` | подставляется из учётки, правится руками — см. ниже |
| Результаты | `result` | `result` | к чему пришли |

## Статус проставляется вручную

Добавлен миграцией `V27`, набор расширен `V28` (31.07). Раньше «идёт» **выводилось** из пустой даты окончания, но одной датой состояние не выразить: тест могут запланировать заранее или приостановить. Теперь `status` — отдельная колонка из трёх ступеней жизненного цикла (`запланировано` / `идёт` / `завершён`, по умолчанию `идёт`), редактируется выпадающим списком в ячейке. По ней же работают фильтр (все три статуса), подсветка строки `.running` (только `идёт`) и счётчики в сводке (Запланировано / Идут / Завершено). Дата окончания стала чисто информационной. Набор значений задаёт фронт (`AB_STATUSES` в `abtests.js`); сервер, как и промо, хранит статус как есть без валидации.

## «Кто тестировал» тянется из учётки

При заведении записи поле заполняется почтой текущего пользователя: `abNewOpen()` берёт её из `CRM.me.email`, а сервер подстраховывает — если поле пришло пустым, `AbTestService.create` подставит `CurrentUser.email()`. Дальше это **обычное текстовое поле**: если тест вёл не тот, кто завёл запись, значение переписывается как любое другое.

Связи с `app.users` у колонки нет намеренно: тестировать может человек без учётки в панели (подрядчик, коллега из соседней команды), а внешний ключ такую запись просто не дал бы завести.

## Доступ

Своя секция RBAC — `abtests` (в `Sections.ALL` и в `Sections.WRITABLE`). Права выданы **копией с `promo`** роль-в-роль прямо в миграции:

```sql
INSERT INTO app.role_section (role_id, section_id, can_read, can_add, can_edit, can_delete)
SELECT role_id, 'abtests', can_read, can_add, can_edit, can_delete
FROM app.role_section WHERE section_id = 'promo'
```

Копируются именно текущие права, а не «всем всё»: у Маркетолога и СЕО промо только на чтение, и А/Б тесты ведут себя так же. Матрица прав по ролям — [[Безопасность и RBAC]].

Пункт NAV гейтится по `me.sections` как обычный раздел (`noAcl` у него нет — в отличие от промо, где флаг остался пережитком, см. [[Оболочка панели (shell)]]).

## Конкурентная правка

Как в промо: раздел правит по одной ячейке и присылает вместе с полем `ver` — тот `timestamp_upd`, который видел браузер. Если в базе он уже другой, приходит `409`, фронт показывает «Строку изменил другой пользователь» и перечитывает таблицу. Пока раздел открыт, чужие правки подтягиваются раз в 30 секунд (`AB_REFRESH_MS`), но **не во время** правки ячейки или заполнения формы — иначе поле выдёргивало бы из-под рук.

Белый список правимых полей — `AbTestService.COLUMNS`; попытка изменить что-то вне его (например `created_by`) отбивается `400 «Поле нельзя менять»`.

Каждая операция пишется в `arch.t_admin_log` под именем таблицы `app.ab_test` ([Аудит и журналирование](Аудит%20и%20журналирование.md)); при конфликте версий запись в журнал не попадает — снимок берётся до правки, но пишется только после успешного UPDATE.

## Фронтенд

`static/js/abtests.js` + `static/css/section-abtests.css` (оформление снято с промо, без правил планирования и строк-разделителей по датам). В разделе есть фильтры по году, тестировщику и статусу, поиск по всем текстовым полям, сводка (всего / запланировано / идут / завершено) и выгрузка CSV. Всё считается на клиенте по всему набору: строк тут единицы-десятки в год, постранично их грузить незачем.
