# Маршрутизация (адреса экранов)

У каждого экрана свой адрес: раздел, подраздел, список, карточка, вкладка карточки, окно заведения. Кнопка «назад» — и в браузере, и системная на телефоне — возвращает на предыдущий экран, ссылку можно переслать, F5 не теряет открытое.

До этого панель была одной страницей без адресов: `openSection` переключала класс `.active`, адрес не менялся никогда. «Назад» уводила со страницы целиком, ссылку на карточку переслать было нельзя, а после перезагрузки терялось всё глубже пары «раздел/подраздел».

Код: `js/router.js` — движок; адаптеры и провайдеры — в самих разделах.

## Схема адресов

Сегмент верхнего уровня — `sid` из `NAV`, второй — `cid` без служебного префикса (`ent-client` → `client`, `up-new` → `new`). Адрес совпадает с идентификатором секции RBAC, второй таблицы соответствий нет.

| Экран | Адрес |
|---|---|
| Главная | `/home` |
| Обзор группы | `/comms`, `/entities`, `/reports`, `/dash`, `/monitoring` |
| Подраздел | `/comms/onelink`, `/dash/deviations` |
| Мастер коммуникаций, канал | `/comms/admin/sms` |
| Промо, архив | `/comms/promo`, `/comms/promo/archive` |
| Блок мониторинга | `/monitoring/mon-campaigns/selection` |
| Сущность: таблицы | `/entities/client` |
| Сущность: список | `/entities/client/client` |
| Сущность: карточка и вкладка | `/entities/client/client/12`, `.../12/comms` |
| Реестр шаблонов, карточка | `/entities/template`, `/entities/template/sms/1001` |
| События: список, карточка, заведение | `/entities/event`, `/entities/event/42`, `/entities/event/new/online` |
| Цепочка | `/journeys/<id>` |
| Настройки | `/settings/<панель>`, `/settings/scheme/new` |

Составной идентификатор шаблона (`канал:код`) разложен на два сегмента: двоеточие в пути пришлось бы кодировать, и ссылка стала бы нечитаемой.

## Устройство

Движок не знает ни про `NAV`, ни про `PANES`, ни про секции — поэтому один и тот же файл работает и в панели, и в настройках. Прикладное живёт в двух местах:

**Адаптер** (`Router.configure`) отвечает за верхние сегменты: `serializeTop` собирает их из модели, `openTop` применяет, `key` называет текущий экран, `home` задаёт стартовый маршрут, `fallback` — куда уйти, если маршрут не разрешился.

**Провайдеры** (`Router.register(ключ, {serialize, apply, ready, title})`) отвечают за глубину внутри экрана. Ключ — **id активной вьюхи**, а не пункт меню: у «Сущностей» подразделов столько, сколько сущностей в схеме, но экран у них один; а «Шаблоны и сегменты» с «Событиями» живут в той же группе на других экранах, и по пункту меню их было бы не отличить.

| Провайдер | Ключ | Где |
|---|---|---|
| Сущности | `view-entity` | `js/entities.js` |
| Реестр шаблонов и мастер | `sec-admin` | `js/template-list.js` |
| События | `sec-event-list` | `js/events.js` |
| Промо | `sec-promo` | `js/promo.js` |
| Цепочки | `sec-journeys` | `journeys.js` |
| Мониторинг | `view-mon-campaigns` | `js/shell.js` |
| Scheme Builder | `scheme` | `settings/index.html` |

### Встраивание без правки мест вызова

`openSection` — функция верхнего уровня классического скрипта, то есть записываемое свойство `window`; через него резолвятся и полтора десятка инлайновых `onclick` в разметке, и вызовы из модулей. Поэтому `Router.configure` ставит **одну обёртку** вместо правки тридцати мест:

```js
wrapped = function () {
  depth++;
  try { return orig.apply(this, arguments); }
  finally { if (!--depth) sync(); }
};
```

Счётчик `depth` схлопывает вложенные вызовы в одну запись истории, а синхронизация читает уже итоговое состояние — адрес никогда не покажет то, что на самом деле не открылось. Тот же механизм доступен снаружи как `Router.batch(fn)`: им собран переход по связи из карточки в карточку (`entGo`) и открытие карточки шаблона или события извне раздела.

> Если `shell.js` когда-нибудь переведут на модуль, обёртка перестанет ставиться. `Router.start()` это заметит и напишет в консоль — молча адреса не отвалятся.

### Когда push, а когда replace

Push — обычная навигация. `Router.replaceNext()` — там, где переход не был намерением человека: отказ доступа, откат на Главную, `applyNavAcl`, исчезновение сущности из схемы, удаление записи, первое применение при старте и приведение адреса к факту после `apply`. Иначе «назад» упирался бы в адрес, которого больше нет.

### Гонка инициализации

Адрес известен сразу, а состав разделов — нет: подразделы «Сущностей» появляются после ответа `/api/me` и загрузки схемы. Поэтому `openTop` отвечает `{pending:true}`, пока группа не знает своих детей, а `entSyncNav` и `applyNavAcl` в конце зовут `Router.navReady()`. Раньше ту же задачу решал костыль `ENT_WANT`, читавший `crmpanel:lastSection` напрямую.

Экран может открываться и в два приёма — карточку шаблона или события сначала надо запросить у сервера. Тогда `apply` возвращает промис, и адрес приводится к факту только после ответа.

Провайдер зовётся и с **пустым хвостом** — это тоже маршрут: так «назад» на голый адрес раздела сворачивает открытую поверх списка карточку или окно.

### Базовый путь

Ресурсы подключены относительными путями, `<base>` в документах не было. По адресу `/entities/client` браузер пошёл бы за `/entities/js/shell.js`. Поэтому в `<head>` обоих документов инлайновый скрипт считает базу (первый известный корень маршрута — для панели, сегмент `settings` — для настроек) и вставляет `<base href>`. Скрипт обязан быть инлайновым и первым: внешний файл сам тянется относительным путём и умер бы первым.

## Что потребовалось от сервера

Обычные пути (без решётки) требуют, чтобы на неизвестный адрес сервер отдавал приложение.

**Spring** — `config/SpaFallbackConfig.java`: перехват 404, а не catch-all, чтобы не трогать раздачу статики. Мимо подмены идут `/api/**` (ручка обязана отвечать ошибкой, иначе фронт примет HTML за ответ — строка вместо объекта в `/api/me` роняет весь ACL в «нет прав») и пути с расширениями ресурсов. Проверка по списку расширений, а не «есть точка»: в маршруте встречаются коды и идентификаторы с точками.

**GitHub Pages** — `404.html`: своего фолбэка у Pages нет, на любой неизвестный путь он отдаёт один этот файл. Он запоминает адрес в `?r=` и уходит на нужный документ (панель или настройки), а тот первым делом возвращает адрес на место через `replaceState`. Один мгновенный переход, в истории — одна запись.

**Вход** — после успешного входа человек возвращается на исходный адрес: он лежит в `requestCache`, а тот настроен матчером на переходы браузера. Без матчера «исходным» оказался бы фоновый `/api/me`, который получает 401 первым, и после входа открывался бы JSON.

## Границы

- `?only=list|dashboard` (внешнее окно реестра шаблонов) — второй, более ранний контракт на URL. При нём маршрутизатор переходит в режим `embedded`: разбирает адрес, но не навигирует и историю не трогает.
- Поиск, фильтры и состояние шестерёнки в адрес не пишутся — они живут в памяти и переживают возврат из карточки в список.
- Защита от циклов: бюджет синхронизаций на кадр. Считаются только записи, которые действительно меняют адрес, поэтому ввод в поиск его не тратит.
