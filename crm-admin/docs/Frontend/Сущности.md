# Сущности

Раздел «Сущности» — CRM-часть панели в духе Salesforce: список записей, карточка записи с вкладками и блоками, колонка связанных объектов. Отличие от остальных разделов в том, что **ни одного захардкоженного подраздела здесь нет**: и меню, и колонки, и поля карточки строятся из схемы, которую рисуют в Scheme Builder ([Страница настроек (settings)](Страница%20настроек%20(settings).md)).

Код: `js/entities.js` (экран), `js/entity-layout.js` (расчёт раскладки), `css/section-entities.css`. Разметка — две секции в `index.html`: обзорная `#view-entities-overview` и рабочая `#view-entity`, рядом с ней отдельный хост модалок `#entModalHost`.

## Откуда берётся модель

Три источника, наложенные друг на друга (`js/entities.js:207`, `js/entities.js:231`):

1. `GET /api/schema` — основной (`js/entities.js:217`);
2. при ошибке — файл `settings/schema/crm-schema.json` (`js/entities.js:236`);
3. поверх — черновик Scheme Builder из `crmpanel:schemaDraft`, накладывается `EntityLayout.mergeDraft` (`js/entities.js:239`).

Черновик накладывается именно наложением, а не заменой: поля возвращаются на свои исходные позиции, удалённые уважаются через `model.deleted` / `model.deletedFields` (`js/entity-layout.js:259`). Иначе правка одного поля в настройках переписывала бы весь порядок полей в панели.

Сегодня в схеме шесть сущностей: `record_type` (служебная), `lead`, `client`, `client_contact_info`, `work` и `template` — и шесть связей, две из них many-to-many через `client_work_link` / `lead_work_link`.

## Подразделы сайдбара строятся сами

В `NAV` группа `entities` объявлена с пустым `children` (`js/shell.js:45`) — их наполняет `entSyncNav()` (`js/entities.js:1509`) и сразу зовёт `renderNav()`. Поэтому сущность, заведённая в настройках, появляется в сайдбаре без правки кода, в том числе по событию `storage` из вкладки настроек (`js/entities.js:1708`).

- id пункта — `ent-<id сущности>` (`js/entities.js:1518`, `js/entities.js:1522`).
- Обычная сущность получает `view:"view-entity"`, `entity:<id>` и `noAcl:true` (`js/entities.js:1521`): серверной секции RBAC у сущностей пока нет, фильтровать по `me.sections` нечем.
- Сущность с полем `source` — исключение. У `template` (`source:"templates"`) пункт ведёт на **готовый экран списка шаблонов**: `view:"sec-admin", adminMode:"list", aclSection:"templates"` (`js/entities.js:1517`). Данные там лежат в БД, а не в браузере, и доступ гейтится обычной серверной секцией `templates`. Подраздел называется «Шаблоны и сегменты», описан в [Мастер коммуникаций (формы)](Мастер%20коммуникаций%20(формы).md).
- Флаг `adminOnly` у самой группы **вычисляемый**: `grp.adminOnly = !grp.children.length` (`js/entities.js:1534`). Без этого роль с выданным доступом к одной сущности видела бы карточку на обзорной странице, но не пункт в сайдбаре.

### Кто что видит

`entAllowed(e)` (`js/entities.js`) по порядку: не «головная» таблица схемы — нет; служебная сущность и переключатель выключен — нет; ни таблиц, ни связок — нет; есть `source` — да (дальше решает RBAC по своей секции, у «Шаблонов и сегментов» это `templates`); нет `window.CRM_ME` — да (демо-режим без бэкенда); админ — да; секция `entities` (зонтик «все сущности») — да; иначе решает секция самой сущности — `ent:<сущность>` в матрице прав, группа «Сущности».

Раньше на этом месте стоял клиентский реестр `crmpanel:entityAccess`: объект в localStorage, который правился из консоли браузера (`entAccessSet`). До сервера он не доходил, у каждого браузера был свой и умел только **сужать** выданное матрицей — причём пустой список читался как «никому», из-за чего раздел не открывался ни одной роли, сколько прав ей ни выдай. Реестр снят, доступ выдаётся только матрицей.

Служебные сущности (`technical`, сейчас это `record_type`) скрыты и в меню, и в обзоре; показать их можно кнопкой на обзорной странице — состояние в `crmpanel:entityShowTech` (`js/entities.js:132`).

## Данные записей живут в браузере

Все записи всех сущностей — один ключ `crmpanel:entityData` (`js/entities.js:29`), запись целиком переписывается в `entStore()` (`js/entities.js:81`). Серверного CRUD у сущностей нет: в `js/entities.js` ровно два запроса, и оба за схемой. При первом заходе раскладывается демо-набор по три записи на сущность (`entSeedData`, `js/entities.js:1546`), отметка о посеве — `crmpanel:entityDataSeed`; уже введённое посев не трогает.

Практическое следствие: данные не переживают чистку хранилища браузера и не видны коллегам. Раздел сделан так осознанно — сначала выверяется модель и раскладка карточки, потом под них заводятся таблицы.

## Три экрана

**Таблицы сущности** — промежуточный экран (`js/entities.js:959`): карточка головной таблицы плюс некликабельные карточки связующих m2m-таблиц. Возврат на него — крошка «← Таблицы сущности» в шапке раздела (`js/entities.js:942`).

**Список записей** (`entListHtml`, `js/entities.js:745`):

- Колонки по умолчанию — первые шесть полей по приоритету типов (`js/entities.js:582`), `related_list` в список не попадает.
- Фильтры по умолчанию — не больше четырёх, сначала `picklist` / `checkbox` / `lookup` (`js/entities.js:609`). Контрол — селект для перечислимых типов, текст для остальных (`js/entities.js:700`).
- Поиск `#entSearch` идёт по склейке значений **видимых** колонок плюс id (`js/entities.js:666`) — искать по колонке, которой нет на экране, было бы гаданием.
- Сортировка кликом по заголовку, направление переключается повторным кликом; числа сравниваются как числа, остальное — `localeCompare` (`js/entities.js:686`).
- Шестерёнка (`entGearHtml`, `js/entities.js:721`) — два блока, «Отображаемые поля» и «Показывать фильтры», со счётчиком `N / 10`. Потолок `ENT_LIST_MAX = 10` (`js/entities.js:566`) применяется и к уже сохранённым наборам: длиннее список перестаёт читаться. Меньше одной колонки не оставить. Набор личный: `crmpanel:entityListCols` / `crmpanel:entityListFilters`, структура «сущность → список полей».

**Карточка записи** (`entCardHtml`, `js/entities.js:883`):

- шапка `.ent-rec-head`: кнопка «← К списку», бейдж типа объекта, строка `таблица · id N`, заголовок из `title_field`, справа отдельным блоком действия «＋ Новая запись» и «Удалить запись»;
- под названием — «подсвеченные» поля (`highlights`) из настроек шапки;
- вкладки (по умолчанию «Детали» и «Коммуникации», `js/entity-layout.js:210`); «Детали» убрать нельзя (`js/entity-layout.js:217`);
- блоки полей: свёрнутость запоминается на время сессии, число колонок 1/2/3 из настроек (`js/entities.js:812`);
- справа — колонка связанных объектов (rail). Она **липкая** (`css/section-entities.css:145`) и держится на всех вкладках, а не только на «Деталях»; на экране уже 1080 px становится обычным блоком под содержимым (`css/section-entities.css:315`), на 640 px таблица списка превращается в карточки (`css/section-entities.css:336`);
- правка — карандаш у поля; сохраняет Enter и клик мимо поля, отменяет Escape (`js/entities.js:1147`, `js/entities.js:1165`). Обязательное поле нельзя очистить (`js/entities.js:1195`). `update_ts` и `user_update` проставляются сами (`js/entities.js:1208`).

Клик по связанному объекту (`entGo`, `js/entities.js:1434`) открывает подраздел головной сущности, но сразу выставляет нужную запись — промежуточный экран таблиц не мигает.

## Заведение и удаление — в модальном окне

Модалка живёт в `#entModalHost` рядом с `#entHost`, а не внутри него: перерисовка списка не должна её закрывать.

- **Создание** (`js/entities.js:1315`): поля разложены теми же смысловыми блоками, что и в карточке, — форма и карточка не расходятся. Поля, скрытые зависимостями, не рисуются вовсе; смена управляющего поля перерисовывает форму на месте (`js/entities.js:1376`). Запись появляется только по «Сохранить» и только если заполнены обязательные — иначе в подвале строка «Заполните: …» (`js/entities.js:1402`). Обязательность бывает условной (`ENT_REQUIRE_IF`, `js/entities.js:286`). id пересчитывается непосредственно перед вставкой (`js/entities.js:1412`), чтобы соседняя вкладка не заняла тот же номер.
- **Удаление** (`js/entities.js:1302`) — своё окно с типом, названием и id записи и прямым текстом «без возможности отменить». `confirm()` браузера здесь не годится: он не показывает, что именно удаляют.

## entity-layout.js — общий расчёт раскладки

Один модуль читают и панель, и настройки (`window.EntityLayout`, `js/entity-layout.js:310`): `js/entities.js`, `settings/object-manager.js`, `settings/scheme-builder.js`. Это и есть причина его существования — настройка и отображение обязаны считать раскладку одинаково, иначе «в настройках выглядит так, а в панели иначе».

Что он решает: канонический список из 22 блоков и всегда-последний блок «Служебные» (`js/entity-layout.js:38`); куда падает поле, про которое настройки нет — `autoBlock()` (`js/entity-layout.js:132`: `id` и `*_ts` в «Служебные», связь в «Связи», чекбокс во «Флаги», деньги и проценты в «Показатели», остальное в «Основное»); итоговый `resolve(e)` — настройки сущности поверх умолчаний, пустые блоки выброшены (`js/entity-layout.js:162`); конфиг карточки — колонки (по умолчанию 2), рельс (по умолчанию включён), вкладки (`js/entity-layout.js:211`).

Сами настройки лежат внутри сущности (`entity.layout`), то есть едут вместе со схемой, — см. [Страница настроек (settings)](Страница%20настроек%20(settings).md).
