# Обзор фронтенда

Фронтенд crm-admin — **одностраничное приложение без сборки**: `index.html` с разметкой плюс подключаемые файлы стилей и скриптов на чистом JavaScript. Никаких фреймворков, бандлеров и npm — файлы лежат в `src/main/resources/static/` и раздаются Spring Boot как статика.

Эта заметка — карта: какой файл за что отвечает, как загружается страница, какие соглашения общие для всех разделов и где искать каждый раздел панели.

## Как загружается страница

В `<head>` (`index.html:11`): CDN `Chart.js 4.4.1` и `xlsx 0.18.5` (нужны «Панели отклонений»), затем `api.js`, `combobox.js`, `wizard.js`, локальный `drawflow.min.js` и `journeys.js` (единственный с `defer`), шрифт и девять файлов стилей.

`api.js` грузится **до** скриптов разделов — они рассчитывают, что глобальный `window.CRM` уже существует.

Скрипты разделов подключены в конце `<body>` (`index.html:2276`): `shell` → `srcbuilder` → `promo` → `abtests` → `reports` → `smscheck` → `entity-layout` → `entities` → `heatmap-*` → `onelink` → `wizard-forms` → `template-details` → `template-list` → `dashboard` → `boot`. Это обычные классические скрипты без `defer`/`async`: они исполняются строго по очереди и делят одну глобальную область видимости, поэтому функции одного файла видны следующим. **Порядок менять нельзя**: `entity-layout.js` обязан идти до `entities.js`, а `boot.js` замыкает список и стартует приложение, когда всё объявлено.

У `entity-layout.js` и `entities.js` в адресе стоит метка версии (`?v=2`) — файлы правятся чаще прочих, и без неё браузер отдавал закешированную пару, где одна половина новая, а вторая старая.

Дальнейший ход — бутстрап `/api/me` и `/api/env`, разобранный в [Клиент API (api.js)](Клиент%20API%20(api.js).md).

## Общие соглашения

- **Глобальная область одна на всех.** Секции не изолированы модулями: функция, объявленная в одном файле, доступна следующим. Отсюда правило про порядок скриптов и «мягкие» вызовы через `typeof f === "function"` — оболочка не должна падать, если файл раздела не загрузился.
- **Секции переключаются классом `.active`** у `<section class="view">`, а не роутером; адрес страницы не меняется.
- **Состояние клиента — в `localStorage` под префиксом `crmpanel:`**; полный список ключей — в [Оболочка панели (shell)](Оболочка%20панели%20(shell).md).
- **Все запросы к шаблонам, цепочкам и учёткам идут через `req()`** из `api.js` — иначе теряются обработка 401 и разбор ошибок. Разделы, живущие на одном-двух собственных эндпоинтах (промо, отчёты, «ЧЕК СМС траффик», сущности), делают `fetch` сами, но повторяют те же правила: `credentials: "same-origin"`, текст ошибки из тела ответа, 401 → `login.html`.
- **Перевод статики — через data-атрибуты**: `data-i18n` (текст), `data-i18n-html` (токен с разметкой), `data-i18n-ph` (placeholder). Ставить `data-i18n` на элемент, внутри которого есть иконка, нельзя — перевод пишет в `textContent`.
- **Права на клиенте — только UX.** `CRM.can(cap, …sections)` и скрытые кнопки нужны для удобства; отказывает всё равно сервер ([Безопасность и RBAC](../Architecture/Безопасность%20и%20RBAC.md)).

## Изоляция стилей: @scope

Стилей по файлу на раздел, каждый обёрнут нативным `@scope` с корнем-идентификатором секции:

| Файл | Корень `@scope` |
|---|---|
| `css/shell.css` | **`@scope` нет вообще** — файл глобальный: переменные, тема, шапка, сайдбар, обзорные страницы, Главная, канва цепочек, загруженные инструменты |
| `css/section-admin.css` | `#sec-admin` |
| `css/section-deviations.css` | `#sec-deviations` |
| `css/section-onelink.css` | `#sec-onelink` |
| `css/section-srcbuilder.css` | `#sec-srcbuilder` |
| `css/section-promo.css` | `#sec-promo` |
| `css/section-abtests.css` | `#sec-abtests` |
| `css/section-reports.css` | `#view-reports, #view-report-embed, #view-report-smscheck` + отдельный блок `#view-report-smscheck` |
| `css/section-entities.css` | `#view-entity` + отдельный блок `#view-entities-overview` |

Благодаря `@scope` порядок подключения после `shell.css` значения не имеет, и правило одного раздела физически не может долететь до другого. Плата за это — **корень надо не забыть дописать**, и это уже дважды приводило к тому, что раздел оставался без стилей.

**Случай первый — «ЧЕК СМС траффик».** Раздел добавили новой секцией `#view-report-smscheck`, повторив разметку отчётов Tableau (`.rp-hero`, `.rp-toolbar`, `.rp-setup`), но в прелюдию `@scope` файла `section-reports.css` его не внесли. Ни одно правило `.rp-*` до него не дошло: панель фильтров разъехалась, подписи, поля и кнопки легли друг на друга. Починка — третий id в списке корней (`css/section-reports.css:2`) плюс свой блок для таблицы `.sc-*` (`css/section-reports.css:275`).

**Случай второй — обзорная страница «Сущностей».** Стили раздела ограничены `@scope (#view-entity)` — это экран данных. Обзор живёт в отдельной секции `#view-entities-overview`, и туда они не долетали: кнопки над карточками оставались системными. Починка — второй блок `@scope (#view-entities-overview)` (`css/section-entities.css:362`), в который продублировано ровно то, что нужно панели, а не весь набор.

Третья ловушка того же рода: **селектор с `html` внутри `@scope` физически невозможен**. `:scope` — это сама секция, а класс темы висит на корневом `<html>`, снаружи области видимости. Поэтому вся светлая добивка вынесена либо в `shell.css`, либо в правило вне `@scope` (`css/section-entities.css:356`, с комментарием прямо на месте).

Практическое правило при заведении новой секции: id секции в `index.html` и корень `@scope` в её CSS проверяются парой, а если секция переиспользует чужую разметку — её id дописывается в прелюдию **чужого** файла, а не копируются правила.

Секции без собственного `@scope`-файла (Главная, все обзорные, `view-heatmap`, `view-mon-*`, `view-uploads`, `sec-journeys`) стилизуются глобальными классами `shell.css` — это осознанно, их разметка на них и построена. За одним стоит следить: `#view-reports-overview` **не входит** в `@scope` файла `section-reports.css`, хотя лежит с ним в одном разделе NAV, — любое правило `.rp-*`, добавленное для обзора, туда не долетит.

## Кто что видит

| Роль | Что доступно (фронт) |
|---|---|
| Без права записи | просмотр своих разделов; `data-readonly` и `CRM.can` прячут кнопки сохранения |
| С правом записи | + создание и редактирование шаблонов, промо, А/Б тестов, записей сущностей |
| ADMIN | + «Цепочки», настроечная админка `/settings`, все разделы NAV |

Права раздаются не ролью-константой, а матрицей «раздел × право» — модель описана в [Безопасность и RBAC](../Architecture/Безопасность%20и%20RBAC.md).
