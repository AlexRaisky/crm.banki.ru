# Планирование промо и А/Б тесты

Два раздела одного типа: общая таблица команды, живущая на сервере, с правкой по одной ячейке. `js/promo.js` (`#sec-promo`) и `js/abtests.js` (`#sec-abtests`) устроены одинаково, поэтому описаны вместе — различия ниже отмечены явно.

Серверная сторона, колонки таблиц и правила чтения — в [Планирование промо](../Backend/%D0%9F%D0%BB%D0%B0%D0%BD%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5%20%D0%BF%D1%80%D0%BE%D0%BC%D0%BE.md) и [АБ тесты](../Backend/%D0%90%D0%91%20%D1%82%D0%B5%D1%81%D1%82%D1%8B.md); контракты — в [REST API](../API/REST%20API.md).

## Общее устройство обоих разделов

- Данные тянутся с сервера при загрузке страницы и **каждые 30 секунд** (`js/promo.js:233`, `js/abtests.js:14`). Тик пропускается, если секция не видна на экране или открыт редактор ячейки (`js/promo.js:315`) — иначе обновление затирало бы набранный текст.
- Правка — поячеечная: клик по ячейке превращает её в поле, рядом появляются ✓ и ✕. Подтверждают Enter (для многострочных — Ctrl+Enter), отменяет Escape, клик мимо сохраняет. Обработчик клика мимо ловится в capture-фазе и сразу открывает следующую кликнутую ячейку (`js/promo.js:1167`) — иначе на каждую правку уходило бы два клика.
- Если значение не изменилось, запрос не уходит вовсе (`js/promo.js:1117`).
- Конкурентные правки разруливает оптимистическая блокировка: вместе с полем уходит версия строки, и на 409 показывается «Строку изменил другой пользователь…» с перечитыванием таблицы (`js/promo.js:262`).
- Права — `CRM.can(cap, 'promo')` (`js/promo.js:239`) и `CRM.can(cap, 'abtests')` (`js/abtests.js:49`). Без права `edit` ячейка рендерится обычным `<td>` **без класса `editable` и без data-атрибутов** — значение видно, но кликнуть не по чему. Кнопки удаления и «+» просто не рисуются. Всё это UX: отказывает сервер ([Безопасность и RBAC](../Architecture/%D0%91%D0%B5%D0%B7%D0%BE%D0%BF%D0%B0%D1%81%D0%BD%D0%BE%D1%81%D1%82%D1%8C%20%D0%B8%20RBAC.md)).
- 403 на чтении рисует в теле таблицы «Нет доступа к разделу» (`js/promo.js:293`).

## Планирование промо

### Одна таблица, а не календарь

Представление одно — таблица, где даты вынесены **строками-разделителями** внутри той же таблицы (`js/promo.js:697`): дата, день недели, а в конце строки кнопка «+» «Добавить запись на эту дату». Выходные подсвечены. Календарной сетки нет намеренно: планируют не «месяц целиком», а конкретные дни, и в сетку не влезают ни база, ни каналы, ни статус.

Две вкладки — «Актуальные» и «Архивные» со счётчиками (`js/promo.js:726`), граница проходит по сегодняшней дате.

Фильтров семь: месяц, продукт, партнёр, канал, ответственный, «есть тотал», свободный поиск (`js/promo.js:596`). Значения списков собираются из фактических данных текущей вкладки (`js/promo.js:559`), кроме каналов — они из закрытого справочника. Над таблицей пять плиток сводки: коммуникаций, тотал-рассылок, запланировано, требуют внимания, каналы (`js/promo.js:626`).

### Заведение записи

Форма — не модалка, а две строки, вставленные в начало таблицы (`js/promo.js:982`). Так видно соседние даты, под которые планируешь.

Обязательны **дата** и **хотя бы один канал** (`js/promo.js:917`); уникальное имя, если заполнено, должно быть из латиницы, цифр и дефиса (`js/promo.js:207`). Продукт, партнёр и база не обязательны — без них просто не соберётся имя коммуникации. Пока есть проблема, кнопка сохранения заблокирована, а под формой идёт живой предпросмотр «Будет создано записей: N» со списком собираемых имён (`js/promo.js:920`).

**Одна запись = один канал**: при нескольких отмеченных каналах уходит по POST на каждый, последовательно (`js/promo.js:964`), и задача может быть своя на канал. Почему так — в [Планирование промо](../Backend/%D0%9F%D0%BB%D0%B0%D0%BD%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5%20%D0%BF%D1%80%D0%BE%D0%BC%D0%BE.md).

Название коммуникации не вводится, а собирается: `канал_promo_продукт_партнёр_уникальноеимя_ддммгг`, для КЦ с суффиксом `day` (`js/promo.js:338`). Пока частей не хватает, в ячейке честно написано, чего именно (`js/promo.js:789`). Это те же правила, что в карточке шаблона и в [Конструктор source и OneLink Builder](%D0%9A%D0%BE%D0%BD%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%82%D0%BE%D1%80%20source%20%D0%B8%20OneLink%20Builder.md).

### Правила планирования и конфликты

Две независимые проверки, обе считаются на клиенте при каждой отрисовке.

**Правила** (`promoAnalyze`, `js/promo.js:357`) — «одно промо» здесь это группа «дата + продукт + партнёр + уникальное имя», то есть одна акция в разных каналах считается один раз:

| Правило | Уровень |
|---|---|
| не больше одной тотал-рассылки в неделю (двух, если в имени есть `-cb` — ставка ЦБ) | предупреждение |
| не больше трёх промо одного продукта в день | нарушение |
| промо одного продукта в день должны идти в разных каналах | нарушение |
| не больше четырёх промо в день | нарушение |
| в день с тоталом остальные промо в том же канале | нарушение |

**Конфликты баз** (`promoComputeClash`, `js/promo.js:488`) — отдельная механика: корзина «день + продукт + канал + база», конфликт засчитывается только если в ней встретились **две разные кампании** (`js/promo.js:531`). Одна кампания, разложенная на несколько строк, конфликтом не считается. Сравнение регистронезависимое, но подсвечивается оригинальное написание — чтобы было видно, что писали по-разному.

Цвета: янтарь — тотал и пересечение баз, коралл — нарушение правила; красный перебивает янтарь (`css/section-promo.css:169`), потому что нарушение правила важнее пересечения.

### Прочее

- Переноса перетаскиванием нет. Дату меняют иконкой календаря в ячейке «Дата» (`js/promo.js:830`) — после сохранения строка сама уезжает в другой блок дат.
- Экспорт CSV выгружает **только то, что сейчас отфильтровано** (`js/promo.js:1197`), 15 колонок вместе с колонкой «Замечания» — текстами сработавших правил. Файл с BOM, чтобы Excel не ломал кириллицу.
- Задача превращается в ссылку на Jira по ключу вида `ABC-123` (`js/promo.js:202`).
- Партнёр вводится свободно, с подсказками из `dictionary.d_partner`; кнопка «+» рядом заводит новое значение в справочник и подставляет то, что вернул сервер. Если такое значение уже загружено, запрос не уходит — поле просто выравнивается по справочнику (`js/promo.js:1261`).
- База — закрытый список из 16 значений плюс поле «своё значение»; хранится строкой через запятую (`js/promo.js:132`).
- Статус прошедшей рассылки, если он не «отправлено» и не «отменено», показывается как «Нужен статус по рассылке» (`js/promo.js:213`). Это только отображение — сам перевод статусов делает сервер при чтении.
- Демо-данных нет: пустая таблица — нормальное стартовое состояние.

## А/Б тесты

Тот же тип раздела: общая таблица на `/api/ab-tests`, поячеечная правка, оптимистическая блокировка, автообновление раз в 30 секунд. Оформление снято с промо, но без блоков, которых здесь нет: правил планирования, строк-разделителей по датам и мультивыбора каналов (`css/section-abtests.css:1`).

Своё:

- **Статус проставляется вручную**, три ступени: «запланировано» → «идёт» → «завершён» (`js/abtests.js:26`). У новой записи по умолчанию «идёт» — её же подсвечивает зелёная полоса и считает счётчик «Идут сейчас».
- «Кто тестировал» у новой записи заполняется почтой текущей учётки (`js/abtests.js:53`), но остаётся обычным текстом: вписать коллегу можно руками.
- Таблица рисуется только после ответа `/api/me` (`js/abtests.js:431`) — иначе она успела бы отрисоваться без прав, со всеми карандашами.
