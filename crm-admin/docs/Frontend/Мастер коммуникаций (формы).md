# Мастер коммуникаций (формы)

Секция `#sec-admin` — главный рабочий инструмент панели: здесь заводят, ищут и правят шаблоны коммуникаций. Одна секция работает в **четырёх режимах** (`setAdminMode(mode)` из `js/shell.js:986`), которые выбираются пунктами сайдбара:

| Пункт NAV | Режим | О чём |
|---|---|---|
| Коммуникации → Мастер коммуникаций | `wizard` | заведение нового шаблона |
| Сущности → **Шаблоны и сегменты** | `list` | витрина всех шаблонов |
| Коммуникации → Просмотр настроек | `view` | карточка сохранённого шаблона |
| Дашборд → Общая статистика | `dashboard` | сводные показатели (демо) |

Список шаблонов открывается **из раздела «Сущности»**, а не из «Коммуникаций»: сущность `template` объявлена с полем `source:"templates"` и потому ведёт на этот готовый экран — см. [Сущности](Сущности.md).

Полоса вкладок `#tabsBar` скрыта **всегда** — режимы выбирает сайдбар, канал в мастере — настроечный блок.

| Файл | За что отвечает |
|---|---|
| `js/template-details.js` | **Ядро раздела**: карточка шаблона (SFD) — и в мастере, и в просмотре; правила имён; предпросмотр; создание и сохранение; пикер просмотра |
| `js/template-list.js` | Список: загрузка страницами, фильтры, сортировка, настройка колонок, инлайн-правка |
| `js/dashboard.js` | Режим «Общая статистика» |
| `js/wizard-forms.js` | Библиотека функций старых форм: формат даты, подсказки полей, поиск и загрузка шаблона |
| `wizard.js`, `combobox.js` | Справочники и редактируемые дропдауны **старых форм** |

## Важно: мастер — это карточка, а не форма

Развёрнутые формы каналов (`#sms`, `#push`, `#email`, `#cc`, `#fa`, `#vk`) **остались в разметке, но недостижимы**: `setAdminMode` всегда прячет `#tabsBar`, а `wizardSetChannel(ch)` снимает `.active` со всех форм и активирует карточку.

Практические следствия, которые экономят время при чтении кода:

- `openTab()`, `collectFormData()`, `saveFromChannelForm()` вызываются только из скрытой разметки — через интерфейс до них не добраться.
- `wizard.js` и `combobox.js` обслуживают **только** эти скрытые формы: все `.combo-input` на странице — поля Communication Name внутри них. Карточка справочники тянет сама, а дропдаун делает нативным `input + datalist`.
- Из `js/wizard-forms.js` в живом пути работают только `formatDateDDMMYY()`, подсказки полей и функции пикера просмотра.
- Формулы имён продублированы: DOM-версии — в `wizard-forms.js` для старых форм, «безформенные» (`sfdComputeCampaignName`, `sfdComputeComname`) — в `template-details.js`. Живая — вторая пара.

## Выбор канала

Настроечный блок — шесть кнопок: **SMS · Mobile-push · E-mail · КЦ · FA · VK**. Как раньше `openTab`, `wizardSetChannel(ch)` сбрасывает `window.CRM_CURRENT = null` — сохранение из мастера всегда идёт как создание.

Отдельной кнопки **Live Activity** нет: это разновидность пуша. В карточке Mobile-push при создании появляется тумблер **«Это Live Activity»** (`js/template-details.js:525`), который переключает сам канал (`push` ↔ `la`) и перерисовывает карточку с LA-полями. Тумблер есть только при создании: у сохранённого шаблона смена канала — это переезд между таблицами.

Полный набор каналов, который знает раздел: `sms`, `push` / `mobile-push`, `email`, `cc`, `fa`, `vk`, `la`.

## Карточка шаблона (SFD)

Одна и та же карточка обслуживает два режима, различаемых полем `SFD_STATE.mode`:

| | создание (`create`) | просмотр |
|---|---|---|
| открывается | `wizardCardOpen(channel)` (`js/template-details.js:879`) | `renderTemplateDetails(data, id)` (`js/template-details.js:38`) |
| контейнер | `#wizardOutput` | `#settingsOutput` |
| поля | все не-readonly сразу открыты на ввод | текст, правка по карандашу |
| строка «Канал» | скрыта | показана, readonly |
| строка «Code» | только у КЦ | показана, readonly |
| секция «Цепочка» | есть (sms/push/email) | нет |
| футер | «Создать шаблон» + «Очистить» | «Сохранить» + «Отменить», как только есть правки |
| сверху | — | «← К списку шаблонов» → «Шаблоны и сегменты» |

Состояние — `SFD_STATE = {id, orig, work, editing, mode, chain, landingAuto}`: `orig` — исходные данные (по ним работает «Отменить»), `work` — рабочая копия, `editing` — какие поля сейчас в режиме ввода. Заготовка нового шаблона (`sfdBlank`, `js/template-details.js:858`) почти вся пустая: единственное непустое значение — `active: true`, плюс для push/LA подставляется базовый deep link. `trigger`, `day` и `sender_name` намеренно оставлены пустыми — заполненное «по умолчанию» поле человек не перечитывает.

Часть флагов в БД отдельных колонок не имеет и при открытии шаблона **восстанавливается из уже сохранённых имён**:

| Флаг | Откуда восстанавливается |
|---|---|
| `cross` | наличие `-cross` в `communication_name` (`js/template-details.js:23`) |
| `is_contact` (`cc_cross`) | префикс `contact_` в `source` (`js/template-details.js:27`) |
| `is_autopromo` | суффикс `-autopromo` в `communication_name` (`js/template-details.js:93`) |
| «Отложенное промо» и дата | шесть цифр в хвосте `source`; если они совпадают с сегодняшним числом, считается, что дату не задавали (`js/template-details.js:130`) |

### Секции и поля

Набор строк зависит от канала (`sfdFieldDefs`, `js/template-details.js:425`); секции сворачиваются кликом по заголовку. Порядок на экране: Основное → Источник и сегментация → Интеграция FA → Контент и ссылки → Live Activity → Служебные параметры и флаги.

**Основное** — «Это Live Activity» (только создание push/la), «Канал» (только просмотр), «Code» / для КЦ «Сегмент (code)», «Статус», далее три поля, которые меняют **само имя кампании**, и потому стоят здесь, а не среди флагов:

- **`is_contact`** (ключ `cc_cross`, только sms и email) — подменяет канал в `campaign_name` на `contact`. Так помечают коммуникацию, которая уходит выгрузкой в контактный центр;
- **`is_autopromo`** (все каналы, кроме КЦ) — вешает суффикс `-autopromo` на communication_name и **убирает дату** из campaign_name: у автопромо нет одной даты рассылки;
- **«Отложенное промо»** — показывается только при `trigger = promo`, и лишь при включённом флаге появляется поле **«Дата в имени кампании»** (`js/template-details.js:550`). Обычное промо берёт в имя сегодняшнюю дату; отложенному нужна дата будущей рассылки, и она задаётся явно.

Замыкает секцию **Communication name** — комбо с подсказками из справочника.

**Источник и сегментация** — «Campaign name» (`source`, **readonly**, собирается сам), «Trigger type», «Product type» (справочник), «Partner name» (комбо + кнопка «+»), «Touch point» (справочник), «Sending day» (только цифры). Для VK добавляется «AB Group». Для КЦ — «Описание сегмента», «Source system» (закрытый список: CALLTRACKING, KASKO, INVEST, INSMORTGAGE, CPA, MPK, OSAGO, RKO), «Host Id», «Kvint campaign Id». Отдельной строки «Сегмент» у КЦ **больше нет**: она дублировала «Code», а в имя кампании сегмент всё равно подставляется из кода.

**Интеграция FA** (только FA) — `fa_id`, `channel_id`, «Need push», `c2d_transport`, `c2d_account`, `ch2d_operator_id`.

**Контент и ссылки** — набор по каналу:

- email — «Email from» (**readonly**, выводится из типа коммуникации) и «Letteros ID»; поля темы нет — тему проставляет отправка;
- sms — «Message text» и «Sender name» (`Banki.ru` / `Bamm.ru`);
- push — «Title», «Message text», «Deep link», «Webview link»;
- fa — «Link title», «Deep link», «Webview link», «Web url», «Action buttons (JSON)»;
- vk — «VK template name», «TTL», «Buttons (JSON)»;
- la — «Title», «Deep link», «Webview link», «Action buttons (JSON)»;
- **cc** — контентных полей нет, секция не выводится.

**Live Activity — параметры активности** (только `la`) — `activity_name`, `la_event`, `la_visualization`, `la_status`, `current_step`, «LA visualization attributes (JSON)».

**Служебные параметры и флаги** — «Communication tunnel», «Business communication type», «Landing page» (`aff_sub3`) и чекбоксы `marketplace`, `cross`, `dialog`, `loyalty`, `national_rating`, `news`, `mobile_app`, плюс `night_send` (кроме FA и VK).

### Landing page выводится из ссылки

Поле `aff_sub3` заполняется само по адресу, который ввели в webview-ссылку (для FA — ещё и в «Web url»); диплинк для этого не используется — он служебный. Правило (`sfdLandingFromLink`, `js/template-details.js:195`):

1. адрес должен быть на `banki.ru` (с любым поддоменом) — чужой домен не даёт ничего;
2. берётся путь после домена;
3. отбрасывается якорь, затем весь query — вместе с ним и utm-разметка;
4. вырезается служебный сегмент `/webview/`: всё, что после него, и есть посадочная страница;
5. пустой путь и голый `/` дают пустое значение.

`https://www.banki.ru/webview/promo/leto?utm_source=push` → `/promo/leto`.

Подстановка **не затирает введённое руками**: карточка помнит последнее автоподставленное значение и обновляет поле, только если оно пустое или совпадает ровно с ним (`js/template-details.js:228`). Срабатывает по завершении ввода, а не на каждый символ, — иначе значение прыгало бы на каждой букве адреса.

### Почему карточка перерисовывается редко

Полную перерисовку `sfdRender()` вызывают только три поля — список `SFD_RELAYOUT = {trigger, delayed, is_la}` (`js/template-details.js:256`), — и ещё случай, когда подстановка сама изменила другие поля (promo-дефолты или landing page).

Причина конкретная: перерисовка пересоздаёт `<input>`, а у нативного `type="date"` при этом сбрасывается набранный сегмент — **дату становилось невозможно ввести**, каждая цифра стирала предыдущую. Поэтому перерисовывать разрешено ровно там, где меняется сам **состав строк** карточки: `trigger` открывает строку «Отложенное промо», `delayed` — строку даты, `is_la` — весь набор канальных полей.

Всё остальное обновляется на месте. Значения, которые считаются сами, помечены в разметке атрибутом **`data-view`**, и `sfdRefreshViews()` (`js/template-details.js:271`) переписывает им только текст. Обновляются при этом не все `data-view`, а лишь три вычисляемых — `source`, `comname`, `email_from` (`js/template-details.js:269`): остальные строки рисуются через форматтер (канал показывается как «SMS», а не `sms`), и сырое значение испортило бы вид.

Третий сдерживатель: приехавший справочник не перерисовывает карточку, пока фокус стоит в поле ввода (`js/template-details.js:321`).

### Подсказки: назначение поля и колонка в БД

У каждой строки есть значок **(i)**. Текст собирается из двух карт: `SFD_HELP` — назначение поля, `SFD_DB` + `SFD_TABLES` — **в какую колонку какой таблицы поле ложится**. Например, `code` у email — это `notice.email_template.trigger_code`, у КЦ — `callcenter.d_segment_properties.segment`; у `channel`, `cross`, `is_contact`, `is_autopromo` и «Отложенного промо» подсказка честно говорит «отдельного поля нет». Таблицы каналов — [Справочники шаблонов](../Database/Справочники%20шаблонов.md).

Тултип рисуется в фиксированный контейнер `#fieldHelpPopup`, а не CSS-подсказкой у строки: та обрезалась краями карточки и секций.

Отдельно живёт старая система подсказок из `wizard-forms.js` — она ищет `.field label` внутри `#sec-admin` и сегодня достаёт только фильтры списка, пикер просмотра, дашборд и скрытые формы. **Карточка ей не пользуется.** Обе системы пишут по-русски и при смене языка не переводятся.

### Правка и сохранение

В режиме просмотра при наведении на строку появляется ✎ (только при праве `edit`), клик превращает значение в `input` / `textarea` / `select` / чекбокс. Числовые поля сделаны текстовыми с `inputmode=numeric` — не `type=number`. Readonly-строки карандаша не имеют.

Как только есть правки, снизу прилипает футер:

- **Сохранить** → `sfdSave()`: пересчёт имён → `CRM.v1ToDto(work)` → `window.CRM_CURRENT = {channel, code}` → `CRM.updateTemplate(...)`; после успеха данные перечитываются с бэкенда и карточка рисуется заново;
- **Отменить** → возврат к `SFD_STATE.orig`.

### Создание

Блок «недостающих полей» держит кнопку «Создать шаблон» заблокированной, пока не заполнены: код (**только у КЦ**), Product type, Touch point, communication_name и контент канала — Letteros ID для email, Message text для остальных, кроме КЦ. При включённой цепочке требования по коду и контенту снимаются: они задаются построчно.

С communication_name есть тонкость: `NoComName` — **обычное значение справочника**, и его же подставляет автогенерация при пустой базе. По значению «поле не трогали» и «выбрали `NoComName` осознанно» не различить, поэтому карточка помнит флаг `comnameTouched`: он взводится при первой правке поля, и с этого момента `NoComName` проверку проходит.

`sfdCreate()` (`js/template-details.js:1040`) → проверка права `add` → пересчёт имён → для email `letteros_id` при необходимости берётся из кода → `window.CRM_CURRENT = null` → `CRM.saveFromV1(d)` → alert с communication_name и выданным бэкендом кодом → перезагрузка списка и чистая карточка.

## Автогенерация имён

### communication_name

`sfdComputeComname(d)` (`js/template-details.js:70`) сначала **срезает все известные флаги** с текущего значения (`sfdStripComnameFlags`) — иначе снятый флаг оставлял бы свой суффикс навсегда, — потом достраивает базу `out-trigger-` партнёром и навешивает флаги заново в фиксированном порядке:

```
[marketplace-] база [-cross][-dialog][-loyalty][-nr][-news][-mobile-app][-autopromo]
```

Если база пустая, результат тоже пустой: флаги без имени не вешаются.

### campaign_name (поле Campaign name / source)

`sfdComputeCampaignName(d)` (`js/template-details.js:137`) работает от объекта данных, не от DOM. Если `trigger` не `promo` и не `trigger`, имя не собирается вовсе, а пустой результат **не затирает** сохранённое значение.

| Канал | Trigger type | Формула |
|---|---|---|
| sms / push / email / fa / vk | `promo` | `{ch}_promo_{product}_{partner}_{comname}_{ддммгг}` |
| sms / push / email / fa / vk | `trigger` | `{ch}_trigger_{product}_{comname}_{day}day` |
| cc | `promo` | `contact_promo_{product}_{partner}_{comname}_{ддммгг}day` |
| cc | `trigger` | `contact_trigger_{product}_{comname}_{segment}_{day}day` |

`{ch}` — не сам код канала, а его «имя в source»: `sms` → `sms`, `push` → **`mobile-push`**, `email` → `email`, `fa` → **`fin-assistent`**, `vk` → `vk`. Канала `la` в этой карте нет — в имя попадает `la` как есть.

Две поправки поверх формул:

- при включённом **`is_contact`** первая часть заменяется на `contact` независимо от канала;
- при включённом **`is_autopromo`** дата не подставляется, и хвостовое `_` тоже не появляется (`js/template-details.js:162`) — иначе имя оканчивалось бы подчёркиванием.

Дата берётся из поля «Дата в имени кампании», если включено «Отложенное промо»; иначе — сегодняшняя (`js/template-details.js:104`).

### Предзаполнение при trigger = promo

Смена «Trigger type» на `promo` сразу проставляет четыре поля (`js/template-details.js:174`): `touch = promo`, `day = 0`, «Communication tunnel» = `adv`, «Business communication type» = `adv`. У промо эти значения одни и те же почти всегда, а промахнуться в них легко: `day` участвует в имени, а `biz_type` — в адресе отправителя. Значения пишутся поверх текущих, а не только в пустые, и подстановка сразу перерисовывает карточку.

### Sender email (только email)

`sfdComputeEmailFrom(d)` — порядок проверок значимый:

| Условие | Адрес |
|---|---|
| touch = `renewal` | `renewal@email.banki.ru` |
| biz_type = `service` | `no-reply@email.banki.ru` |
| biz_type = `info` | `inform@email.banki.ru` |
| trigger = `trigger` и biz_type = `adv` | `offers@email.banki.ru` |
| trigger = `promo` и biz_type = `adv` | `advice@email.banki.ru` |
| иначе | `newsletter@email.banki.ru` |

### Когда пересчитывается

`sfdRecalcNames()` вызывается при открытии карточки, при создании, при сохранении и при правке любого поля из `SFD_NAME_KEYS` (`trigger`, `product`, `partner`, `comname`, `day`, `segment`, `touch`, `cc_cross`, `autopromo`, `delayed`, `promo_date` и все флаги имени) либо `biz_type`. `touch` попал в список не ради имён, а ради адреса отправителя — `renewal` там первое условие.

## Цепочка (Is chain)

Секция появляется в карточке **только при создании** и только для `sms`, `push`, `email`.

1. Чекбокс «Is chain — шаблон на каждый день цепочки» открывает поле дней и таблицу.
2. Дни вводятся числами через запятую (`0,3,7`); ввод санитайзится на лету — пробелы и `;` превращаются в запятую, чтобы «0 3 7» не слиплось в «037», позиция курсора при этом восстанавливается. Дни проверяются на числовость и уникальность, уже заполненные значения при перегенерации сохраняются.
3. Колонки зависят от канала: sms — Message Text; push — Title, Message Text, Deep Link, Webview link; email — Letteros Id. Эти же поля временно исчезают из «Контента и ссылок» — они задаются построчно; если после этого секция пуста, она не выводится вовсе.
4. Обязательные по строкам: sms — message; push — title и message; email — letteros_id. Незаполненное поле — alert с номером дня.
5. Создание идёт **строго последовательно, по шаблону на день**: общая часть карточки очищается от по-дневных полей (иначе текст уезжал бы туда, где его не вводили), к ней подмешиваются значения строки и её `day`, `source` пересчитывается под конкретный день. Для email код шаблона берётся из Letteros Id. Цепочка — всегда создание.

## Предпросмотр сообщения

Правая колонка карточки (`sfdRenderPreview`, `js/template-details.js:1327`), перерисовывается при каждом изменении:

- **SMS** — «пузырь» на макете телефона с именем отправителя;
- **Push** — карточка уведомления плюс **проверка на переполнение**: сравнивается реальная высота с видимой и пишется «Текст помещается…» либо «Не помещается: заголовок / текст — часть будет скрыта под „ещё“. Заголовок — 1 строка, текст — до 4 строк»;
- **FA / VK** — бабл мессенджера с кнопками, разобранными из JSON (`action_buttons` / `buttons`; поддерживаются оба варианта ключа подписи, `title` и `label`); для FA при `need_push` — примечание, что сообщение продублируется пушем;
- **Email** — `iframe` с версткой из Letteros (`https://app.letteros.com/webv/<letteros_id|code>`, `sandbox`, `referrerpolicy="no-referrer"`) и ссылкой «Открыть в Letteros ↗». Загрузка откладывается на 500 мс, а если адрес не изменился, карточка не трогается вовсе — иначе `iframe` пересоздавался бы на каждый введённый символ и бил в Letteros. Если адреса нет, но в тексте лежит HTML, он рисуется через `srcdoc` в полностью закрытом `iframe`;
- **КЦ и Live Activity** — предпросмотра нет.

Макетов iOS/Android у пуша нет: поле `SFD_STATE.pushOS` в коде объявлено, но нигде не читается.

## Справочники карточки

`sfdEnsureDicts(channel)` (`js/template-details.js:328`) тянет четыре справочника по одному разу за загрузку страницы: Touch point, Product type, Communication name (с параметром канала) и Partner name. Провалившаяся загрузка запоминается пустым списком и не повторяется — иначе каждая перерисовка била бы в упавший эндпоинт.

`sfdDictOpts` при необходимости подмешивает **текущее значение**, если его нет в списке: иначе открытие старого шаблона со снятым из справочника значением молча подменяло бы его первым пунктом. Product и Touch — строгие селекты; communication_name и partner_name — комбо (`input` + `datalist`): новые значения заводятся регулярно, строгий список их бы отсёк.

### Пополнение справочника из карточки

У поля **Partner name** рядом с вводом стоит кнопка **«+»** (видна при праве `add`): она заносит введённое значение в `dictionary.d_partner` и подставляет обратно то, что вернул сервер — он мог вернуть уже существующее написание. Если такое значение уже есть в загруженном списке (регистр не важен), запрос не уходит вовсе, поле просто выравнивается по справочнику. После успеха `campaign_name` пересчитывается сразу.

Какие поля так умеют, задаёт карта `SFD_DICT_ADD` (`js/template-details.js:374`) — пока в ней только партнёр: остальные списки правятся осознанно, а партнёр появляется в работе раньше, чем кто-то успевает добавить его в справочник.

## «Шаблоны и сегменты» — список

### Загрузка

Данные грузятся **страницами по 50 записей с бесконечной прокруткой** (`js/template-list.js:171`): собираются фильтры, сортировка, `limit` и `offset` и зовётся `CRM.listTemplates`. Следующая страница подтягивается, когда до конца остаётся меньше 300 px; сентинел показывает «Загрузка…» или «— всё загружено —». Устаревшие ответы отбрасываются по счётчику запросов.

Отдельно считаются итоги: `CRM.countTemplates()` — всего и активных, `CRM.facetsTemplates()` — реальные значения продуктов, точек касания, типов и партнёров для наполнения фильтров.

Функция называется `loadMockData()`, но никаких mock-файлов не читает — имя историческое. Аварийный набор `FALLBACK_LIST_TEMPLATES` существует, но практически недостижим: ошибку загрузки страницы список глотает сам.

### Фильтры, поиск, сортировка

- Шесть фильтров: канал, продукт, touch point, trigger type, партнёр — мультиселекты, статус — обычный селект. Внутри фильтра значения складываются по ИЛИ, между фильтрами — И. Фильтрация и поиск идут **по всей базе на сервере**: клиентский фильтр поверх страницы в 50 строк врал бы.
- **Скрытый в настройках фильтр не применяется** — иначе выборка молча сужалась бы значением, которого не видно на экране.
- Строка поиска уходит на сервер параметром `q`.
- Сортировка кликом по заголовку, повторный клик разворачивает направление, сортирует сервер по всей выборке.
- Счётчик: «N элементов (показано N из TOTAL — листайте, чтобы загрузить ещё) · Отсортировано по „…" · всего TOTAL (активных: A, неактивных: B)».

### Колонки и настройка отображения

`LIST_COLUMNS` (`js/template-list.js:11`): Канал, **Live Activity**, Code / ID, Название, Продукт, Touch point, Trigger, Партнёр, Статус, **Source type**, **Letteros ID**. Последние две — только для чтения: оба поля участвуют в нейминге и в поиске, и менять их по одной ячейке, не видя остальных, опасно — для этого есть карточка.

Панель-шестерёнка содержит блоки «Отображаемые поля» и «Показывать фильтры»; настройки лежат в `crmpanel:listCols` / `crmpanel:listFilters`, кнопка «По умолчанию» сбрасывает. Потолок — **10 колонок и 10 фильтров** (`js/template-list.js:47`), он применяется и к уже сохранённым наборам, которые могли скопиться до его появления. По умолчанию показываются первые десять колонок, то есть Letteros ID включается вручную. Последнюю колонку снять нельзя. Смена колонок — только перерисовка, смена набора фильтров — перезапрос.

### Live Activity внутри канала Push

В списке LA **не отдельный канал**: в колонке «Канал» у него бейдж Push, а принадлежность к LA показывает отдельная колонка. Это повторяет модель карточки, где LA заводится тумблером в мастере Mobile-push.

- В фильтре «Канал» пункта Live Activity нет, а выбранный **Push отправляет на сервер оба значения** (`channel=push&channel=la`, `js/template-list.js:192`) — на бэке `la` по-прежнему самостоятельный канал.
- Колонка `is_la` вычисляется в `CRM.apiItemToList` из канала, в данных её нет, и она только для чтения.
- Сортировка по ней поддержана на сервере, иначе клик по заголовку молча сортировал бы по коду.
- Колонка добавлена в уже существующие наборы одноразовой доливкой (`listMigrateCols`, отметка в `crmpanel:listColsAdded`) — иначе её увидели бы только те, кто нажмёт «По умолчанию». Снятая вручную колонка обратно не возвращается, и встаёт она на своё место из набора по умолчанию, а не в хвост.

### Правка прямо в таблице

У ячейки при праве `edit` есть карандаш; клик открывает редактор, рядом появляются ✓ и ✕, работают Enter и Escape. Тип редактора задаёт `LIST_COLUMNS[].edit`: `text`, `bool`, `select` (строгий список — канал, trigger) и `combo` — `input` + `datalist` со значениями справочника.

Пока `combo` только у **Партнёра**: справочник тянется **только при первом открытии карандаша** — список грузится всем, а правит его меньшинство. Текущее значение всегда подмешивается в варианты, иначе снятое из справочника значение не предложилось бы обратно.

Сохранение идёт «оптимистично»: значение сразу видно в таблице, затем читается полный шаблон, в нём меняется одно поле (для email правка кода тянет за собой `letteros_id`) и уходит как UPDATE. Если сервер отказал — значение откатывается и показывается alert. Ключ колонки не всегда совпадает с ключом поля карточки, и без карты соответствия правка «Названия» уходила в несуществующее поле и молча откатывалась.

Клик по ссылке Code/ID или Названия ставит `window.CRM_CURRENT` (дальше сохранение пойдёт как UPDATE), тянет полный шаблон и открывает его в «Просмотре настроек». При ошибке сети показываются частичные данные из строки списка.

Чего в списке **нет**: массовых действий (чекбоксы строк нарисованы, но ни один обработчик их не читает) и экспорта.

## «Просмотр настроек»

Самостоятельный пункт NAV; ACL следует правам раздела `admin` — см. [Оболочка панели (shell)](Оболочка%20панели%20(shell).md).

Сверху — **пикер в два шага**: «1. Канал» (семь кнопок, включая Live Activity) → «2. Шаблон». Во втором блоке три поля поиска — по `source_type`, по Letteros ID (появляется только для email) и по Code — и выпадающий список.

Список строится запросом **на сервер** с каналом и поисковой строкой, забирается не больше 500 позиций, и если упёрлись в потолок — в первой строке так и написано («первые 500 — уточните поиск»). Подпись пункта — `код — source_type` (если пуст, берётся communication_name) плюс пометка «(неактивный)».

Поиск по коду ищет на бэкенде по всей базе и оставляет **точное** совпадение кода или Letteros ID. Код уникален внутри канала, но может совпадать между каналами: показывается первый, про остальные пишется подсказка с предложением искать через список.

Дальше открывается та же карточка SFD, что и в мастере, но в режиме просмотра.

## «Общая статистика» (дашборд)

**Данные полностью демонстрационные**: `js/dashboard.js` не делает ни одного запроса к API, глобальная `DASHBOARD_DATA` безусловно получает зашитый набор (комментарий в коде: «Дашборд пока вне скоупа — оставляем демо-данные»). Кнопка «Обновить данные» не ходит на сервер, а слегка рандомизирует числа и переставляет время последнего обновления.

Что нарисовано: четыре KPI, статистика по каналам, «Коммуникаций на одного человека», «Индикатор перегрева базы» (порог 3: Норма / Внимание / Перегрев), размер активной аудитории, пересечение каналов, доля недоступных ни в одном канале, топ-5 активных сегментов, топ-5 с худшей доставкой, среднее число коммуникаций на пользователя за 7 и 30 дней, доля получивших больше N сообщений, топ-10 перегруженных сегментов, отписки после X контактов, столбики отправок и дублей за 7 дней (нарисованы вручную, без Chart.js) и топ-5 шаблонов. Режим «По конкретному шаблону» работает от второго демо-набора, список шаблонов в селекте зашит прямо в разметку.

## Права

Раздел смотрит на `sfdCan(cap)` = `CRM.can(cap, 'admin', 'templates')` (`js/template-details.js:17`) — клиентское зеркало серверного `AccessGuard`:

| Проверка | Что скрывает |
|---|---|
| `edit` | карандаши в карточке и в ячейках списка, футер «Сохранить/Отменить», сам вызов сохранения |
| `add` | кнопки «Создать шаблон» и «Очистить» (вместо них текст «Нет прав на создание шаблонов»), кнопка «+» у справочника партнёров, сам вызов создания |

Право достаточно иметь в **любом** из разделов `admin` / `templates`. Право `delete` в разделе не используется — кнопки удаления шаблона в интерфейсе нет, хотя метод `CRM.deleteTemplate` существует. Видимость самих режимов управляется навигацией, а не `can()`. Всё это UX: сервер проверяет права на каждом запросе.
