## Контуры

| Контур | Адрес | Приложение | БД |
|---|---|---|---|
| prod | домен через nginx :80 | `crm-admin-app-prod` | `crm-admin-db-prod` :5432 |
| preprod | 127.0.0.1:8081 | `crm-admin-app-preprod` | `crm-admin-db-preprod` :5433 |
| test | 127.0.0.1:8082 | `crm-admin-app-test` | `crm-admin-db-test` :5434 |

```bash
ssh -L 8081:127.0.0.1:8081 -L 8082:127.0.0.1:8082 user@сервер   # UI preprod/test
ssh -L 15432:127.0.0.1:5432 user@сервер                          # БД прод в DBeaver: localhost:15432 / crm / crm
```

Имя базы и пользователь у всех трёх одинаковые — контур различает только порт. Спросить у самой базы:

```sql
SELECT DISTINCT env FROM app.schema_owned;   -- prod | preprod | test
```

## Обновление сервера

```bash
cd crm.banki.ru/crm-admin && git pull                      # ветка admin-panel
docker compose -f docker-compose.yml -f docker-compose.server.yml build app-prod
docker compose -f docker-compose.yml -f docker-compose.server.yml \
  up -d --no-deps --force-recreate app-test                # сначала test
docker compose -f docker-compose.yml -f docker-compose.server.yml \
  up -d --no-deps --force-recreate app-preprod app-prod    # потом preprod и prod
docker exec crm-admin-nginx nginx -s reload                # ОБЯЗАТЕЛЬНО после пересоздания

./scripts/reset-test.sh          # сброс test с нуля
./scripts/refresh-preprod.sh     # preprod = копия прода
```

`build app-prod` собирает общий образ `crm-admin:local` — его подхватывают все три контура. `--no-deps` не даёт перезапустить БД, `--force-recreate` нужен потому, что тег образа не меняется.

**Про `nginx -s reload`:** nginx резолвит `app-prod` один раз на старте и держит IP в памяти. После `--force-recreate` адрес меняется, и без reload домен может отдавать чужой контур — так уже случалось. Правки только в `.env` пересборки не требуют, достаточно `up -d --force-recreate`.

## Диагностика

```bash
docker compose ps
docker logs crm-admin-app-prod --tail 50
docker restart crm-admin-nginx
curl -s http://localhost/nginx-health

# очередь синка (PENDING → SENDING → OK, при неудаче обратно в PENDING, после 10 попыток ERROR)
docker exec crm-admin-db-prod psql -U crm -d crm -c \
 "select id, channel, operation, local_code, prod_code, status, attempts, left(coalesce(last_error,''),200) from app.prod_sync order by id desc limit 10;"
# застрявшие SENDING: обработчик сам их НЕ переотправляет — сначала проверить в проде, доехала ли строка
docker exec crm-admin-db-prod psql -U crm -d crm -c \
 "select id, channel, local_code, timestamp_upd from app.prod_sync where status='SENDING';"
# перезапустить упавшие / очистить
docker exec crm-admin-db-prod psql -U crm -d crm -c \
 "update app.prod_sync set status='PENDING', attempts=0, last_error=null where status='ERROR';"
docker exec crm-admin-db-prod psql -U crm -d crm -c "delete from app.prod_sync;"

# метки ETL
docker exec crm-admin-db-prod psql -U crm -d crm -c "select * from app.sync_watermark;"
# последние действия пользователей
docker exec crm-admin-db-prod psql -U crm -d crm -c \
 "select timestamp_cr, action_user, table_name, operation from arch.t_admin_log order by id desc limit 15;"
# роли и их права
docker exec crm-admin-db-prod psql -U crm -d crm -c \
 "select r.name, rs.section_id, rs.can_read, rs.can_add, rs.can_edit, rs.can_delete from app.role r join app.role_section rs on rs.role_id=r.id order by r.sort_order, rs.section_id;"
# шаблоны
docker exec crm-admin-db-prod psql -U crm -d crm -c \
 "select channel, code, communication_name, campaign_name, active_flag from template.d_template order by channel, code;"
# что Scheme Builder завёл в базе своими руками
docker exec crm-admin-db-prod psql -U crm -d crm -c "select env, schema_name, table_name from app.schema_owned order by 1,2,3;"

# связь с внешним продом напрямую
docker run --rm -e PGPASSWORD='пароль' postgres:16 psql -h ХОСТ -p ПОРТ -U ЮЗЕР -d БАЗА -c "select 1;"

# бэкап
docker exec crm-admin-db-prod pg_dump -U crm crm | gzip > backup_$(date +%F).sql.gz
```

Первый экран при проблемах с продом: `/settings` → **Диагностика**. Ручные прогоны синка и ETL — кнопками там же (`POST /api/admin/etl/run`, `/etl/run-full`, `/api/admin/prod-db/process`, `/reconcile/import-all`); **«Импортировать всё из прода»** перезаписывает все наши строки прод-версией и очередь не смотрит.

## Частые правки — куда идти

| Задача | Где |
|---|---|
| Поля формы, значения по умолчанию | `index.html` + `wizard.js` |
| Формулы `communication_name` / `campaign_name` | `js/wizard-forms.js`, в карточке — `js/template-details.js` |
| Подсказки к полям мастера | `js/wizard-forms.js` (`FIELD_HELP_TEXTS`) |
| Стили раздела | `css/section-<раздел>.css`; общее — `css/shell.css`. Новая секция обязана быть в прелюдии `@scope`, иначе правила до неё не долетят |
| Правила кодов, обязательные поля прода | `service/UnifiedTemplateService` |
| Что уезжает в прод | `service/TemplateStore.prodPayload` |
| Как строится INSERT в прод | `service/prod/ProdDbService.insert` |
| Пополнить справочники | `insert into dictionary.d_touch_point (value) values ('…');` |
| Разделы RBAC | `service/Sections` + `NAV` в `js/shell.js` + `SECTION_LABELS` в `admin-users.js` (все три места) |
| Роли и права | `/settings` → «Управление доступом» (в БД — `app.role`, `app.role_section`) |
| Правила входа и URL-доступа | `security/SecurityConfig` |
| Узлы Flow Builder | `journeys.js` (`NODE_TYPES`) + `service/flow/MaterializationService` |
| Подразделы и поля «Сущностей» | не в коде: модель рисуется в `/settings` → Scheme Builder |

## Конфигурация (`.env`)

Inline-комментариев в `.env` нет — всё после `=` считается значением.

| Переменная | |
|---|---|
| `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_URL` | БД контура |
| `APP_PORT[_PREPROD\|_TEST]`, `DB_PORT[_PREPROD\|_TEST]`, `APP_BIND`, `DB_BIND` | порты и привязка; на сервере оба bind — `127.0.0.1` |
| `SPRING_PROFILES_ACTIVE` | `docker` (БД в контейнере + Flyway) или `prod` (внешняя корпоративная БД, Flyway выключен) |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | супер-админ |
| `APP_EMAIL_DOMAIN` | домен почты (пусто ≠ «без ограничений», см. [[Безопасность и RBAC]]) |
| `PROD_DB_URL[_PREPROD\|_TEST]`, `PROD_DB_USER`, `PROD_DB_PASSWORD`, `PROD_DB_CONNECT_TIMEOUT_MS`, `PROD_DB_TIME_ZONE` | внешняя прод-БД |
| `ETL_ENABLED`, `ETL_INTERVAL_MS`, `ETL_FULL_CRON`, `ETL_OVERLAP_MINUTES`, `ETL_INITIAL_DELAY_MS` | ETL «прод → мы» |
| `REMEMBER_ME_KEY`, `REMEMBER_ME_DAYS`, `SESSION_TIMEOUT` | сессии |
| `SESSION_COOKIE`, `REMEMBER_COOKIE` | имена кук (свои на контур) |
| `ADMIN_LOG_TABLE` | физическое имя журнала действий (нужно на профиле `prod`) |
| `APP_ENV`, `FEATURES_DEV`, `JOURNEYS_MOCK` | имя контура, dev-фичи, хранилище цепочек |

Не через `.env`, а параметрами приложения: `app.prodsync.ok-ttl-minutes` (сколько держать доставленные записи очереди, по умолчанию 10) и `app.prodsync.stuck-minutes` (через сколько считать `SENDING` зависшим, 5).
